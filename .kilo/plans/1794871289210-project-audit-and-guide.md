# Аудит проекта и обновление учебника

## Цель и границы

- Провести актуальный аудит MVP, объяснить корректные Git-термины, дать приоритетный план дальнейшей разработки D&D-мастера и сохранить обновлённый учебник в отдельном файле.
- Старый `ARCHITECTURE_GUIDE.md` не удалять и не перезаписывать. Новая версия должна иметь отдельное имя, например `ARCHITECTURE_GUIDE_2026.md`.
- На этом этапе не менять приложение, настройки, миграции и Git-ветки. Существующие изменения рабочего дерева и неотслеживаемые файлы сохранить.
- Считать бесплатность жёстким ограничением для самого приложения и его runtime-сервисов. Пользователь отдельно подтвердил уже оплаченную подписку OpenCode Go за $10 на месяц для coding-агента; это допустимая отдельная стоимость разработки, но Go нельзя подключать как провайдера D&D-мастера. Основная бесплатная конфигурация приложения — локальная Ollama и PostgreSQL/pgvector в Docker. Не полагаться на облачные бесплатные тарифы как на гарантированно бесплатные; отметить требования локального железа и электричества.

## Подтверждённое состояние

- Репозиторий — один проект с `backend/` и `frontend/` (монорепозиторий); это структура репозитория, не стратегия ветвления.
- Текущий срез: React 19 + TypeScript + Vite; FastAPI, SQLAlchemy async, Alembic; PostgreSQL 17 + pgvector; OpenAI-совместимые HTTP-адаптеры для чата и embeddings; Ollama описана как локальный вариант. Backend требует Python 3.14+; Docker Compose запускает БД.
- Поток хода: браузер отправляет cookie-аутентифицированный запрос; API проверяет владельца кампании и лимит запросов; сервис мастера сохраняет сообщение, по запросу рассчитывает проверку на сервере, ищет фрагменты SRD через embeddings/pgvector, формирует prompt из system-инструкции, резюме, истории и найденных правил, вызывает LLM и сохраняет ответ; резюме обновляется отдельным вызовом.
- Кампания сейчас создаётся без вступительного сообщения; чат показывает ожидание действия. «Осмотр» не представлен отдельным типом действия или логикой: пользователь может вручную указать проверку, но система не обязана трактовать свободную фразу как исследование окружения.
- SRD-корпус не включён в репозиторий и импортируется отдельно. Тесты подменяют LLM, embeddings и кубик; описаны команды backend/frontend проверок.
- Проектная политика разрешает OpenCode Go для coding-агента, но запрещает его для игрового трафика; это не конфликтует с оплаченной подпиской пользователя. Для приложения README описывает локальную Ollama, а также облачный сценарий. `config.py` имеет OpenAI default и, по проведённому аудиту, не содержит обещанного блокирования Go URL. Это не доказывает, что сейчас приложение использует OpenAI: фактическое значение задаётся локальным `backend/.env`; сам `.env` не проверять на секреты и не менять. Документация должна различать default в коде и активную локальную настройку, и обозначить риск неожиданной платной конфигурации при отсутствии/неверном `.env`.
- Точная терминология: «структура репозитория» — организация каталогов; «стратегия ветвления / Git workflow» — правила работы с `main`, feature-ветками и слияниями. По доступным признакам есть `main`, `backend_dev`, `feature/character-sheet`, GitHub remote и feature-ветка с tracking; обязательного CI и формального стандарта коммитов не обнаружено. Для одиночного MVP достаточно стабильного `main` и короткоживущих feature-веток; постоянную интеграционную ветку вводить только при реальной необходимости.
- На момент аудита Git-агент обнаружил изменённые backend-файлы, новую миграцию и неотслеживаемый `nul`. Это только описание состояния рабочей копии: мы не знаем, кто и с какой целью создал эти изменения, поэтому не называем их «чужими». Это не причина начинать новую сессию. В текущем документальном плане не нужно менять исходники; если позднее потребуется править пересекающиеся файлы, сначала свериться с их актуальным содержимым и сохранить существующие правки.

## Рекомендуемый порядок развития

1. Сначала сделать бесплатный локальный путь однозначным: сохранить локальную Ollama как рекомендуемую конфигурацию приложения, отделить её от подписки Go для coding-агента и объяснить, что облачный API может тарифицироваться отдельно. Проверить и согласовать default/валидацию endpoint с политикой, чтобы исключить случайное направление игрового трафика в Go; если облачный провайдер остаётся разрешённой ручной опцией, не запрещать его целиком. Покрыть политику endpoint тестами.
2. Прежде чем расширять поведение, зафиксировать сценарии приёмки мастера и прогнать baseline на локальной модели. Нужны примеры формулировок «осматриваюсь» и синонимов, пустого/минимального контекста, провала retrieval, недоступности LLM и повторного запроса.
3. Сделать вступление кампании: разумные настройки по умолчанию, место/тон/предыстория персонажа и первая сцена; обеспечить сохранение вступления в истории и понятный fallback при ошибке модели, чтобы пользователь не получил пустой чат. UI оставить минимальным.
4. Улучшить исследование окружения на уровне намерения, а не набора точных фраз: воспринимать свободный текст как осмотр, давать атмосферное описание только на основании заданной сцены/состояния кампании, при необходимости предлагать Perception/Investigation или уточнять действие. Не утверждать, что мастер «видит» отсутствующий в контексте мир; явно отделять нарративное решение от проверяемой механики SRD.
5. До расширения генерации утвердить политику контента и покрыть её тестовыми случаями. Разрешать уместную грубую лексику, мрачное вымышленное фэнтези и повествовательное насилие; не одобрять реальную ненависть/травлю/призывы к насилию; отказывать в сексуальном содержании с несовершеннолетними, груминге и эксплуатации, а также в практических инструкциях по реальному вреду и незаконным действиям. Ввести системные ограничения и безопасный fallback; не считать локальную модель гарантированным модератором. Учитывать конкретные ограничения выбранного провайдера.
6. После каждого этапа добавлять backend-тесты через имеющиеся fake-провайдеры, затем вручную оценивать качество на Ollama; фронтенд менять только для минимально необходимого выбора начального тона/показа вступления.

## Действия для обновления учебника

1. Перед написанием сверить детали по актуальным файлам и тестам, особенно зависимости, модели, переменные конфигурации, API-поток, миграции, ограничения и Git-состояние. Не выводить секреты из `.env`.
2. Создать новую версионированную Markdown-копию в корне, не меняя старый файл. Сохранить доступное новичку изложение на русском и структуру исходного запроса из четырёх частей: архитектура и ASCII-поток; технологии и роль каждой; словарь 10–15 терминов; D&D/RAG, память и подбор контекста.
3. Добавить актуальный раздел «Что уже работает / чего пока нет» и отдельный раздел о терминологии Git, текущей стратегии веток и минимальной рекомендации без ненужной перестройки.
4. Добавить приоритетный roadmap выше, раскрыть бесплатный локальный стек и явно отметить обнаруженные несоответствия. Отличать подтверждённую реализацию от рекомендаций и планируемого поведения.
5. Проверить новую документацию на совпадение с кодом, отсутствие секретов, сохранность старого файла и корректность ссылок/команд. Не запускать миграции и не изменять рабочую конфигурацию в рамках документальной задачи.

## Проверка и условия завершения

- Новая версия учебника существует отдельно; старый `ARCHITECTURE_GUIDE.md` остался нетронутым.
- Все технические утверждения в учебнике сверены с текущим кодом/конфигурацией; отдельно описаны подписка Go только для coding-агента, локальный бесплатный runtime приложения и риск облачной конфигурации по умолчанию.
- Рекомендации разделены на то, что делать следующим, и то, что не нужно менять: в частности, не требуется перестраивать Git workflow для текущей одиночной разработки.
- Никакие исходники, миграции, настройки, ветки, игнор-листы и существующие пользовательские изменения не изменены.
