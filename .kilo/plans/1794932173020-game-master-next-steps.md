# Следующие шаги: D&D-мастер

## Цель и подтверждённые решения

Улучшить игровой опыт вертикального среза, не раздувая минимальный UI и сохранив бесплатный локальный путь на Ollama. Механика остаётся на backend; LLM не назначает и не рассчитывает броски.

- «Я осматриваюсь» и вопрос «что вокруг?» по умолчанию дают игровое описание без броска. Распознаваемый активный поиск может запустить серверную проверку Perception или Investigation; для первого среза сервер использует базовый DC 15. Неоднозначность не должна порождать выдуманный бросок: мастер уточняет действие. Обычное описание окружения не отказывает из-за отсутствия SRD.
- Удалить выбор DC на клиенте. Автоматическая классификация и расчёт принадлежат backend; сохранить результат проверки в существующей metadata. Не расширять этот этап до полной механики боя или состояния сцены.
- При создании кампании генерировать персональную вступительную сцену LLM на русском языке, используя персонажа и необязательное короткое пожелание о жанре/тоне/сеттинге. Пожелание хранить для всех последующих ходов.
- Если LLM недоступна или не возвращает пригодную сцену, кампанию не создавать; вернуть понятную ошибку с возможностью повторить. Шаблонный fallback пользователь не выбрал.
- Разделить свободное создание вымышленного мира и правила: мастер вправе создавать атмосферу, места, NPC и события, но игровые правила и утверждения о механике должны опираться на SRD; нельзя выдавать выдуманное правило за канон.
- Допустить мрачное взрослое фэнтези, уместную грубую лексику, повествовательное насилие и предрассудки между вымышленными группами без одобрения реальной дискриминации. Запретить сексуальный контент с несовершеннолетними, груминг/эксплуатацию, любые сцены насилия с несовершеннолетними, реальные призывы к ненависти, травле или насилию, а также практические инструкции причинения вреда/незаконной деятельности. При запрещённом сюжете использовать краткое безопасное перенаправление.
- Сначала реализовать локальную best-effort политику без платного moderation API. На ПК пользователя (Intel Core i5-11400, 16 ГБ DDR4, RTX 3060 12 ГБ) отдельно проверить небольшую локальную модель-модератор; не считать одновременную загрузку с основной 14B моделью гарантированно возможной. Если эксперимент не проходит критерии памяти, задержки и качества, оставить best-effort.

## Порядок реализации

1. **Игровая интерпретация осмотра.** В `game_master.py` отделить игровой нарратив от SRD-механики и внедрить серверный детерминированный маршрут для поддерживаемых русских формулировок свободного поиска. Простое наблюдение обстановки проходит без проверки. Явный поиск скрытых деталей может выбрать Perception/Investigation и вызвать существующий серверный `resolve_check` с DC 15; не переносить бросок или DC в LLM. Уточнять действие, если классификация неоднозначна. Убрать ручной выбор DC и техническую подачу проверки из чата; сохранить игроку возможность сформулировать действие обычным текстом.
2. **Вступление кампании и постоянный контекст.** Добавить ограниченное необязательное поле пожелания в форму и `CampaignCreate`, хранить его в `campaigns` отдельным полем с Alembic-миграцией, возвращать через `CampaignPublic` и передавать в prompt каждого хода. При создании сгенерировать сцену с учётом имени/вида/класса/предыстории персонажа и пожелания. Передавать пользовательское пожелание как недоверенный контекст, не как инструкцию. Сохранить вступление первым assistant-сообщением существующего журнала; новый API чтения сообщений не нужен. Не создавать кампанию, пока генерация не удалась. В промпте и экране чата показать место, происходящее и естественную зацепку для первого действия.
3. **Контент-политика и безопасные отказы.** Добавить серверную policy к prompt мастера и отдельный локальный best-effort слой проверки входа и ответа перед вызовом/сохранением LLM. Для явного срабатывания не отправлять запрещённый запрос модели; сохранить безопасный отказ/перенаправление как ответ обмена. Проверять также созданную вступительную сцену и недоверенные пожелания. Не вводить внешние платные moderation-сервисы. Не обещать абсолютную безопасность: эвристики могут пропустить сложные формулировки, а чрезмерно широкие правила — блокировать обычное фэнтези.
4. **Эксперимент с локальной модератор-моделью.** Только после best-effort тестов подобрать модель с проверенной лицензией и Ollama-совместимым запуском. Измерить качество на фиксированных разрешённых/запрещённых примерах, задержку полного хода и пиковое использование VRAM/RAM при основной модели. Принять её только если не ломает бесплатный локальный сценарий; иначе оставить опциональной/отказаться без регрессии основного пути.
5. **Бесплатность и защитные конфиги.** Сверить defaults `config.py` с локальным Ollama-путём из `.env.example`, чтобы приложение не выбирало платный облачный endpoint незаметно. Добавить тестируемую блокировку запрещённых OpenCode Go URL в runtime, как уже заявлено в `OPENCODE_GO_POLICY.md`; не читать и не менять `backend/.env`. Документировать, что Ollama/модели работают локально, но требуют подходящего оборудования, а бесплатность хостинга/электроэнергии не гарантируется.
6. **Git-процесс и бесплатный CI.** Термин «гит архитектура» заменить на точные: модель ветвления, стратегия слияния и процесс интеграции. Оставить короткоживущие feature-ветки от `main`; промежуточную `merge-ДД-ММ-ГГГГ` использовать только для крупной интеграции/параллельной работы, а не как обязательный лишний шаг для каждой одиночной задачи. Добавить бесплатный CI для pull request с backend Ruff/pytest (PostgreSQL + pgvector service), frontend lint/build; `main` обновлять только после успешных проверок. Если хостинг/квота CI не подходит, сохранять ручные проверки обязательными. Не менять Git-историю или удалённые ветки.

## Контракты и данные

- Новый параметр создания кампании — необязательное текстовое пожелание с верхним лимитом длины; неизменяемый контекст возвращается в API и входит в system context. Это единственное обязательное изменение схемы БД в выбранном объёме.
- Вступительная сцена хранится обычным `campaign_messages` assistant-сообщением, а не дублируется новым полем или endpoint.
- Проверка поиска хранится в уже существующей JSONB `metadata`; определить, нужны ли поля «тип намерения/автоматическая проверка», не меняя публичный response без необходимости. Если клиент больше не выбирает check, убрать устаревшее поле `check` из контракта либо оставить только явно ограниченный совместимый режим после анализа клиентов; сейчас единственный клиент — этот frontend.
- Контент-политика и модерация не требуют отдельной таблицы или новой платной зависимости. Отдельная модель-модератор может потребовать настройку провайдера, но остаётся необязательной.

## Тесты и приёмка

- Backend: параметризованные русские примеры «я осматриваюсь», «смотрю вокруг», «что я вижу вокруг?», «хочу понять, что вокруг меня находится» дают игровой ответ без фразы «такого действия нет»; простой обзор не бросает кубик; явный активный поиск запускает один фиксированный серверный бросок DC 15; неоднозначный запрос не бросает кубик; клиент не может навязать результат/DC; идемпотентный повтор не бросает повторно.
- Prompt/RAG: при отсутствии найденных источников мастер всё равно может описать вымышленную атмосферу/сцену, но не утверждает правила D&D; найденные SRD-источники продолжают прикладываться. Убедиться, что свободная сцена не теряется из последующего контекста.
- Создание кампании: персональная сцена и пожелание сохранены, первая запись — assistant, история открывается сразу; ошибка/timeout/пустой ответ LLM не оставляет кампанию или orphan-сообщение и возвращает retryable 503/504.
- Policy: тесты запрещённых запросов/ответов и безопасного перенаправления; разрешённые мрачные темы, грубая лексика и конфликт вымышленных фракций не блокируются общими ключевыми словами. Проверить prompt injection в пожелании и текстах истории.
- Конфиг: известный Go endpoint отклоняется; локальный Ollama допускается; никаких ключей в frontend, Git или логах.
- Проверки проекта: `uv run ruff check app`, `uv run pytest -q`, `npm.cmd run lint`, `npm.cmd run build`; тесты используют fake LLM, fake embeddings и фиксированный кубик, не платный API. Интеграционно проверить Alembic upgrade на тестовой БД.

## Наблюдения по текущему проекту и Git

- MVP уже имеет FastAPI/SQLAlchemy/Alembic, PostgreSQL + pgvector, заменяемые Chat/Embedding providers, fake-провайдеры, идемпотентность и advisory lock. Это подходящая база; переписывание RAG, frontend-стека или схемы чата не требуется.
- Сейчас `SYSTEM_PROMPT` запрещает выдумывать любые факты за пределами SRD и резюме, что противоречит запросу на генерацию сцены; `run_turn` не передаёт сведения о персонаже; создание кампании создаёт пустую память и не пишет приветствие.
- Сейчас бросок считает backend, но запрос принимает DC от клиента, а frontend вручную показывает ability/skill/DC. `config.py` по умолчанию указывает OpenAI и не блокирует OpenCode Go; `.env.example` указывает Ollama. В актуальном checkout отсутствует `.github` CI workflow.
- В истории есть feature-ветка `feature/character-sheet` и integration-ветка `merge-17-11-2026`, затем коммиты на `main`; раньше были `backend_dev` и `merge_28_10_2026`. Это модель ветвления/интеграции, не «Git-архитектура». Сам граф не подтверждает запуск тестов перед merge. Текущий checkout на `main`, рабочее дерево чистое.
- Remote ведёт на GitHub, но публичная страница вернула 404, а `gh` CLI недоступен; видимость и branch protection не подтверждены. Перед включением GitHub Actions/правил защиты проверить права и квоту; ничего удалённого не менять без явного запроса.
- Требование «всё бесплатно» обеспечивается локальной конфигурацией и отсутствием новых платных API, но не может гарантировать нулевую стоимость железа, электричества, хостинга или GitHub private-runner сверх лимитов. Совместимость и лицензия каждой локальной модели должны быть проверены до выбора.

## Вне объёма

Полный combat engine, хранение структурированного состояния сцены/скрытых объектов, многопользовательские кампании, смена RAG-хранилища, переписывание frontend и абсолютная гарантия content moderation. Для scene-specific DC и надёжного выявления скрытых угроз позже потребуется структурированное состояние сцены; фиксированный DC 15 — только осознанное MVP-упрощение.
