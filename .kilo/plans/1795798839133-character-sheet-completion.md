# План: доделать модуль чарника (создание + ведение листа)

## Контекст

MVP работает end-to-end, код соответствует `docs/ARCHITECTURE.md`. **Не трогаем** LLM/модель/провайдера: пользователь нашёл вариант и просит оставить ИИ-мастера в покое до реализации его идеи.

Что уже есть:
- Backend: полный CRUD персонажей (`api/v1/characters.py`), серверный каталог и расчёт производных значений (`rules/character_options.py:271`), `PATCH` с частичным обновлением и пересчётом (`services/characters.py:46`), тесты включая левел-ап (`tests/test_characters.py:73`, `:185`).
- `GET /rules/character-options` (`api/v1/rules.py:15`) уже отдаёт каталог + `limits`.
- Frontend: форма создания и лист персонажа в одном файле `frontend/src/CharacterPage.tsx` (480 строк); используется только `create`/`delete` (`api.ts:97`), `PATCH` нигде не вызывается; характеристики захардкожены (`8/14/12/16/10/10`), уровень всегда `1`.
- `users.is_active` / `email_verified_at` есть в схеме, но не используются — **не относится к этой задаче**.

Что добавляем: генерация характеристик по каталогу, редактирование листа, правка текущих HP, повышение уровня, отображение спасбросков/инициативы/пассивной внимательности.

## Зафиксированные решения

| # | Решение | Выбор |
|---|---|---|
| 1 | Направление | Чарник (не подтверждение аккаунта / сброс пароля) |
| 2 | Объём | Создание + ведение листа, без миграций и новых зависимостей |
| 3 | Бюджет point buy | **Проверять на сервере** (выбор пользователя, не клиентский вариант) |
| 4 | Старые строки | **Legacy-режим без миграции** |
| 5 | `current_hp` при левел-апе | Не трогать (растёт только `max_hp`) |

Обоснованные решения планировщика (явно зафиксировать при реализации):
- **Только детерминированные методы**: `manual`, `standard_array`, `point_buy`. Случайный «4d6 drop lowest» **не добавляем** — это бросок кубика, а по инварианту №1 механика считается только сервером; `services/dice.py` не трогаем.
- **Каталог методов на сервере** в `GET /rules/character-options`, а не хардкод в TS (инвариант №3 «клиенту не доверяем»).
- **`ability_score_method` хранится в `data` (JSONB)** — миграция схемы не нужна. Это **не** колонка `characters`.
- **Никакого пересчёта D&D-механики на клиенте**: HP/КБ/модификаторы/спасброски приходят с сервера в `data` и показываются в листе. На клиенте только остаток бюджета point buy (чистая арифметика) как подсказка.
- **Редактирование инлайн** на карточке листа (переключатель «Редактировать»), без новых роутов: форму вынести в переиспользуемый `CharacterForm`.

## Контракт и правила валидации

### Каталог (`GET /rules/character-options` → ключ `ability_generation`)

```json
{
  "score_range": {"min": 3, "max": 18},
  "methods": [
    {"key": "manual", "label": "Вручную"},
    {"key": "standard_array", "label": "Стандартный массив", "values": [15,14,13,12,10,8]},
    {"key": "point_buy", "label": "Покупка очков", "budget": 27,
     "min": 8, "max": 15,
     "costs": {"8":0,"9":1,"10":2,"11":3,"12":4,"13":5,"14":7,"15":9}}
  ]
}
```

### Поле `ability_score_method`

- `CharacterCreate`: **обязательное**, `Literal["manual","standard_array","point_buy"]`.
- `CharacterUpdate`: **необязательное**, тот же `Literal`, `None` не допускается (добавить в `REQUIRED_UPDATE_FIELDS`).
- Значение попадает в `values` через `model_dump` (`exclude_none=True` / `exclude_unset=True`) и **должно быть записано в `data["ability_score_method"]`**, а не в `result` (такой колонки нет, иначе `Character(**values)` упадёт).

### Проверка в `build_character_values` (новый хелпер, `CharacterRulesError` → 422)

| Метод | Правило |
|---|---|
| `manual` | каждое значение `3..18` (существующая проверка) |
| `standard_array` | мультимножество шести значений ровно `[15,14,13,12,10,8]` |
| `point_buy` | каждое `8..15` и сумма `costs[score] <= 27` |
| неизвестный | `CharacterRulesError` |

Разрешение метода на `PATCH`:
1. Если в `values` есть `ability_score_method` — использовать его (и перезаписать `data`).
2. Иначе взять `existing.data.get("ability_score_method")` — **читать из `getattr(existing, "data")` до `base.update(values)`**, иначе отправка `data` в PATCH затрёт его.
3. Иначе метод `None` = legacy-строка.
4. Если метод `None`:
   - `existing is None` (create) → недостижимо из-за обязательного поля, но оставить защитный `422`;
   - `PATCH` **меняет** любую характеристику → `422` с сообщением «Укажите метод генерации характеристик»;
   - `PATCH` **не меняет** характеристики (имя, заметки, `current_hp`, `level`) → бюджет не проверяем, диапазон `3..18` и каталог проверяем как раньше, метод в `data` не пишем.
5. Если метод задан — записать `data["ability_score_method"] = method` и выполнить проверку по таблице.

## Риски и крайние случаи

- **Обязательное поле ломает тесты и любых внешних клиентов** `POST /characters` — обновить оба `character_payload()` и задокументировать изменение контракта в `ARCHITECTURE.md`.
- **Затирание `data` при PATCH**: `build_character_values` берёт `base["data"]` из `values`, если `data` передано. Форма обязана всегда слать `skill_proficiencies`, а legacy-метод читать из `existing.data` **до** `base.update(values)`. Добавить тест на `PATCH` с `data` без потери навыков.
- **Legacy + смена класса**: у старого персонажа (Wizard/Sage) навыки `Arcana/History` станут недопустимы для Fighter → `422`; UI должен предложить перевыбрать навыки до отправки.
- **Point buy max 15 vs текущий диапазон 3..18**: у проекта нет расовых бонусов к характеристикам, поэтому `8..15` — намеренное ограничение именно метода; `manual` остаётся `3..18`, значения `16` в существующих тестах допустимы.
- **Никакого дублирования формул D&D в TS** — иначе расхождение с сервером и нарушение инварианта №1/№3.
- `CharacterUpdate` запрещает `null` для `data`/`max_hp`/`current_hp` — форма не должна слать `null` в этих полях; `notes: null` допустим.

## Откат / миграция

Схема БД не меняется, Alembic-миграция **не создаётся** (`uv run alembic upgrade head` запускается только как проверка). Откат кода безопасен: `data.ability_score_method` — безобидный дополнительный ключ JSONB, legacy-строки не изменены. Новые клиенты без обязательного поля на create получат честный `422`.
