# AGENTS.md — правила для coding-агента

Это единственная точка входа. Прочитай этот файл целиком и следуй ему.
Проект — AI D&D Master: FastAPI + PostgreSQL/pgvector backend и React/Vite frontend
в одном репозитории. Мастер — LLM, но вся игровая механика считается на сервере.

## Контекст-бюджет: что читать

1. **Всегда:** `AGENTS.md` (этот файл).
2. **Архитектура:** `docs/ARCHITECTURE.md` — единственный источник архитектурных фактов
   для агента. Читай его перед задачей, затрагивающей API, БД, prompt, retrieval,
   конфиг или тесты. Не перечитывай без необходимости.
3. **Код и тесты важнее документов.** Если документ расходится с кодом — правда в коде;
   обнови `docs/ARCHITECTURE.md` в той же задаче.
4. **Не открывать без явной просьбы пользователя:**
   - `docs/human/**` — большой учебник для человека;
   - `docs/archive/**` — устаревшие документы, оставлены только для истории;
   - `.kilo/plans/**` — исторические планы задач (кроме плана текущей задачи);
   - `backend/README.md` — человеческая инструкция запуска; открывай только для задач
     про локальную установку, Ollama или импорт SRD (команды есть выше);
   - `backend/data/srd/srd-5.2.1.md` — данные корпуса (~1.6 МБ), читать только
     точечно при работе над импортом/чанкингом;
   - `node_modules/`, `.venv/`, `dist/`, `.run/`, кеши.
5. **Не создавай новые `*.md` в корне.** Документы для агента — в `docs/`,
   для человека — в `docs/human/`, история — в `docs/archive/`.
6. Если задача неоднозначна — сначала уточни цель и границы, не разрастайся в рефакторинг.

## Сохранность архива

- Не удаляй и не перемещай файлы, каталоги и содержимое внутри `docs/archive/` без
  отдельного, явного разрешения пользователя на конкретное действие.
- Не очищай `docs/archive/` и не используй для него операции с рекурсивным удалением.
  Это правило действует, даже если архивный файл кажется устаревшим, дублирующимся,
  неотслеживаемым или мешает текущей задаче.
- Если действие над `docs/archive/` кажется необходимым, сначала запроси у пользователя
  явное разрешение, назвав точный путь и последствия. Изменения в остальных каталогах
  регулируются обычным объёмом текущей задачи и другими правилами проекта.

## `.env`: чтение и изменения

- `backend/.env` можно открывать **только на чтение**. Не копируй его содержимое
  в ответы, логи, коммиты и сообщения другим агентам.
- Изменять `.env` можно только после явного разрешения пользователя. Сначала
  объясни, какой ключ и зачем меняется, дождись ответа, затем правь через `edit`.
- Не обходи это через `bash`, `sed`, `python`, `mv`, `rm` или редиректы. Такие
  команды и правки `.env` настроены как `ask` (проектный `kilo.json` и глобальный
  конфиг Kilo).
- `backend/.env.example` — шаблон без секретов; его можно читать и править свободно.

## Проект в двух абзацах

Пользователь регистрируется, создаёт персонажа и личную кампанию, затем отправляет
сообщения мастеру. Backend проверяет cookie-сессию и владельца, при необходимости сам
бросает d20 и считает проверку, ищет фрагменты SRD в pgvector, собирает prompt из
системной инструкции, резюме кампании, броска, источников и последних сообщений,
вызывает OpenAI-совместимую LLM и сохраняет ответ. Резюме обновляется фоновой задачей.

Механика (кубик, модификаторы, DC, успех) — только серверный Python. Модель описывает
последствия и не придумывает правила, броски и новые проверки. Это ключевой инвариант.

## Команды

Backend (из `backend`):

```powershell
uv run ruff check app
uv run pytest -q
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --port 8000 --loop app.core.loop:selector_loop_factory
```

Frontend (из `frontend`):

```powershell
npm.cmd run lint
npm.cmd run build
```

Проект целиком: `start.bat` из корня; остановка: `start.bat stop`.
Нужны Docker (PostgreSQL 17 + pgvector), `uv` (Python 3.14+) и Node.js 22+.
Тесты используют отдельную БД `dnd_test` и fake-провайдеры, реальный ключ не нужен.

## Инварианты

- Не переносить расчёт бросков/DC на клиент или LLM; не доверять результату с клиента.
- Не позволять модели выдумывать правила: только найденные фрагменты SRD и резюме;
  при отсутствии источников — честный отказ.
- Все запросы персонажей и кампаний фильтровать по `user_id`.
- Сохранять идемпотентность `client_message_id` и advisory-lock кампании.
- Не терять журнал сообщений при ошибках LLM; повтор не должен дублировать обмен.
- Не логировать и не отдавать секреты, пароли, cookie и токены.
- Тесты — через существующие fake-провайдеры и фиксированный кубик.
- Новые зависимости — только при явной необходимости, с обоснованием.

## Политика провайдера (обязательно)

OpenCode Go разрешён только для coding-агента и типичного coding-трафика.
**Запрещено** направлять в Go трафик приложения, backend, скриптов, тестов и генерации
контента D&D-мастера, а также отправлять туда диагностические запросы. Не хранить
ключи OpenCode в `backend/.env`, примерах и коде. Если просят нарушить — предупреди,
предложи локальную Ollama (`http://localhost:11434/v1`) или другого провайдера и
выполняй только после явного выбора альтернативы. Подробности — `OPENCODE_GO_POLICY.md`.

## Стиль работы

- Python: `ruff`, async SQLAlchemy, Pydantic-схемы, русские сообщения об ошибках для UI.
- Frontend: TypeScript, React 19, без новых UI-библиотек без запроса.
- Комментарии в коде — только если пользователь попросил.
- Правки минимальные и по задаче; не переписывай соседний код «заодно».
- Перед началом задачи проверяй ветку (`git status -sb`). Не смешивай несвязанные
  изменения в одной ветке: новая задача или крупный блок — отдельная короткоживущая
  ветка от `main`; имя ветки должно отражать объём работы, а не одну из затронутых фич.
- Промежуточную ветку `merge-ДД-ММ-ГГГГ` от `main` создавай для крупной интеграции
  или параллельной работы, а не как обязательный шаг для каждой одиночной задачи.
  В `main` сливай только если проверки прошли и проблем не найдено.
- CI в `.github/workflows/ci.yml` запускает backend Ruff/pytest (PostgreSQL + pgvector)
  и frontend lint/build на pull request. Успешный CI не отменяет локальные проверки ниже.
- После изменений запускай релевантные проверки: `uv run ruff check app`,
  `uv run pytest -q`, `npm.cmd run lint`, `npm.cmd run build`.
- Не коммить, не пушить и не создавать PR без явной просьбы.

## Текущее состояние (2026-11-17)

MVP работает end-to-end: у кампании есть вступительная сцена, свободный текст распознаёт
намерение поиска на сервере (фиксированный DC 15), действует best-effort политика
контента, а `config.py` блокирует OpenCode Go на старте. Известные пробелы:
нет структурированного состояния сцены и полноценного combat engine, локальная
модель-модератор не внедрена, CI добавлен, но доступность GitHub Actions для репозитория
не подтверждена. Roadmap и подробности — `docs/ARCHITECTURE.md`, раздел 10.
