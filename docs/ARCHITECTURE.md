# D&D Master: архитектура проекта

**Статус:** канонический документ для coding-агента.
**Обновлено:** 2026-11-17, сверено с кодом в `backend/app`, `frontend/src`, `backend/tests`.
**Правило:** если этот файл расходится с кодом или тестами — правда в коде; обнови этот файл в той же задаче.

## 1. Что это

Веб-приложение, в котором пользователь регистрируется, создаёт персонажа, создаёт личную
кампанию и обменивается сообщениями с «мастером». Мастер — текстовая LLM: она описывает
сцену и последствия, но **не управляет механикой**. Броски, модификаторы и сложность
считает сервер на Python; правила для ответа ищутся в SRD 5.2.1 через pgvector.
Мастер вправе придумывать атмосферу, места, NPC и события вымышленного мира, но
утверждения о правилах D&D подтверждает только найденными фрагментами SRD.

## 2. Стек и порты

| Часть | Технологии | Адрес |
|---|---|---|
| Frontend | React 19, TypeScript, Vite, react-router | `http://localhost:5173` |
| Backend | Python 3.14+, FastAPI, SQLAlchemy 2 async, Alembic | `http://localhost:8000` (`/docs`, `/health`) |
| БД | PostgreSQL 17 + pgvector, Docker Compose | `localhost:5433` снаружи |
| LLM | Любой OpenAI-совместимый API: `/chat/completions`, `/embeddings` | базовый URL из `LLM_BASE_URL` |

Локальная бесплатная конфигурация — Ollama (`http://localhost:11434/v1`). Фактические
значения лежат в `backend/.env`; агент не открывает этот файл. Шаблон — `backend/.env.example`.
Локальный путь не создаёт плату за API, но требует подходящего оборудования; стоимость
электричества, хостинга и CI-раннеров сверх бесплатных лимитов не гарантируется.

## 4. Поток одного хода

Создание кампании (`POST /api/v1/campaigns`) — отдельный путь: сервер проверяет персонажа,
при необходимости проверяет необязательное пожелание `premise` политикой контента, затем
просит LLM сгенерировать персональную вступительную сцену. Кампания, память и первое
assistant-сообщение создаются одной транзакцией только после пригодной сцены; ошибка или
непригодный ответ модели не оставляет кампанию и возвращает retryable `503/504`.

Эндпоинт хода: `POST /api/v1/campaigns/{campaign_id}/messages`.

1. Cookie-сессия проверяется в `api/deps.py`; запросы к кампании фильтруются по владельцу.
2. Проверяется лимит `chat_rate_limit_per_minute` (по умолчанию 30/мин на пользователя).
3. Загружается кампания, её персонаж и последние сообщения.
4. Сервер определяет намерение по тексту игрока (`app/rules/intent.py`). Обычное наблюдение
   и неоднозначная формулировка не бросают кубик; явный поиск скрытого запускает
   `resolve_check` с DC 15 (Perception или Investigation). Клиент не передаёт DC, навык
   или результат броска.
5. Пользовательское сообщение сохраняется вместе с намерением и броском в `metadata`.
   `client_message_id` делает повтор идемпотентным: повторно кубик не бросается, возвращается
   уже сохранённый обмен.
6. Текст игрока проверяется best-effort политикой контента. При явном срабатывании модель
   не вызывается: пользовательское сообщение и безопасное перенаправление сохраняются
   обычным обменом, обновление резюме не планируется.
7. Выполняется поиск SRD: embedding вопроса, косинусное расстояние в pgvector, top-k=4.
8. Собирается prompt: системная инструкция + персонаж + пожелание кампании как недоверенные
   данные + резюме + намерение хода + результат проверки + найденные фрагменты SRD +
   последние 12 сообщений.
9. Вызывается LLM; ответ проходит проверку политики и сохраняется вместе с броском и
   источниками. При нарушении сохраняется безопасное перенаправление.
10. В `BackgroundTasks` планируется обновление структурированного резюме отдельным вызовом.

Дополнительно действует advisory-lock на кампанию (`pg_advisory_xact_lock`), чтобы
параллельные запросы не создавали дубликаты. Нумерация сообщений — `sequence`, уникальна
внутри кампании.

Ошибки:
- retrieval упал → ответ без источников, ход продолжается;
- таймаут LLM → `504`, сообщение пользователя уже сохранено, безопасный повтор;
- провайдер недоступен → `503`, сообщение сохранено;
- LLM недоступна или вернула непригодную сцену при создании → `503/504`, кампания не создана;
- запрещённое пожелание кампании → `422`, кампания не создана;
- частые сообщения → `429`;
- нет владения кампанией/персонажем → `404`.

## 5. API (`/api/v1`)

| Метод и путь | Назначение |
|---|---|
| `POST /auth/register` | регистрация, `201` |
| `POST /auth/login` | вход, ставит httpOnly cookie |
| `GET /auth/me` | текущий пользователь |
| `POST /auth/logout` | выход, `204` |
| `GET/POST /characters` | список и создание персонажа |
| `GET/PATCH/DELETE /characters/{id}` | чтение, изменение, удаление |
| `GET /rules/character-options` | доступные виды, классы, предыстории, навыки |
| `GET/POST /campaigns` | список и создание личной кампании; `POST` вызывает LLM для вступления |
| `GET/DELETE /campaigns/{id}` | чтение и удаление |
| `GET /campaigns/{id}/messages?limit=` | история, `limit` 1..500 (по умолчанию 100) |
| `POST /campaigns/{id}/messages` | ход мастера |

`POST /campaigns` принимает `name`, `character_id` и необязательное `premise` (до 500
символов). Поле `check` в запросе хода удалено: проверку назначает сервер по намерению.
Все ответы с персонажами/кампаниями проверяют владельца. `password_hash` и токены
сессий наружу не отдаются.

## 6. Данные

- `users` — email в нижнем регистре, Argon2-хеш пароля.
- `sessions` — хранится только хеш токена, срок жизни и метаданные.
- `characters` — характеристики хранятся в диапазоне 1..30, но приложение валидирует
  3..18; уровень 1..20, вычисляемые HP/AC/speed проверяются сервером; произвольные
  данные — в `data` (JSONB).
- `campaigns` — владелец + принадлежащий ему персонаж, необязательное пожелание `premise`
  (тон/жанр/сеттинг) и первая вступительная сцена в журнале.
- `campaign_memories` — структурированное резюме: `facts`, `goals`, `npcs`, `locations`,
  `open_threads`.
- `campaign_messages` — роль, текст, `sequence`, `client_message_id`, `metadata` (намерение,
  бросок, источники, признак вступления). Уникальность: `(campaign_id, sequence)` и
  `(campaign_id, client_message_id)`.
- `srd_chunks` — `source`, `section`, `title`, `content`, `license`, `embedding VECTOR(1024)`,
  HNSW-индекс с `vector_cosine_ops`, уникальный `chunk_key`.

## 7. Инварианты, которые нельзя ломать

1. Механика — только сервер: кубик, модификаторы, DC, успех/провал. Модель не придумывает
   броски и не меняет результат. Автоматический DC поиска — 15, решение о проверке
   принимает детерминированный серверный код, а не LLM.
2. Свободная вымышленная сцена разрешена, но правила D&D не выдумываются: утверждения о
   механике опираются на найденные фрагменты SRD; при их отсутствии модель описывает
   атмосферу и честно не выдаёт выдуманное правило за канон.
3. Все выборы персонажа валидируются по серверному каталогу; клиенту не доверяем.
4. Любой доступ к персонажу/кампании фильтруется по `user_id`.
5. Повтор запроса с тем же `client_message_id` не создаёт второй обмен и не бросает кубик
   повторно.
6. Ошибка обновления резюме не отменяет ход и не теряет журнал сообщений.
7. Секреты и `.env` не попадают в клиент, логи, ответы и Git.
8. Провайдер модели заменяем через `ChatProvider`/`EmbeddingProvider`; тесты используют
   fake-провайдеры и фиксированный кубик.
9. Политика контента — серверный best-effort слой до и после LLM; при явном срабатывании
   запрещённый текст не уходит модели, а в журнал сохраняется безопасное перенаправление.
   Абсолютная гарантия модерации не заявляется.
10. Текст игрока, история и `premise` — недоверенные данные, а не инструкции для модели.

## 8. Конфигурация (значения по умолчанию)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_BASE_URL` | `http://localhost:11434/v1` | локальная Ollama, а не платный облачный endpoint |
| `LLM_CHAT_MODEL` | `qwen3:14b` | модель мастера |
| `LLM_EMBEDDING_MODEL` | `qwen3-embedding-cpu` | локальные embeddings |
| `RETRIEVAL_TOP_K` | 4 | сколько фрагментов SRD попадает в prompt |
| `RECENT_MESSAGE_LIMIT` | 12 | сколько последних сообщений видит модель |
| `MAX_MESSAGE_LENGTH` | 4000 | максимум символов в сообщении |
| `CHAT_RATE_LIMIT_PER_MINUTE` | 30 | лимит ходов на пользователя |
| `LLM_TIMEOUT_SECONDS` | 120 | таймаут HTTP-запроса к модели |
| `LLM_MAX_OUTPUT_TOKENS` | 700 | максимум токенов ответа |
| `LLM_TEMPERATURE` | 0.7 | температура ответа |
| `LLM_EMBEDDING_DIMENSIONS` | 1024 | обязана совпадать со схемой `srd_chunks` |

При старте `config.py` отклоняет: `SameSite=None` без `Secure`, wildcard в CORS,
размерность embeddings, отличную от 1024, и `LLM_BASE_URL` на OpenCode Go
(`/zen/go` или `/inference/go`). Pay-as-you-go endpoint OpenCode не блокируется, но
использовать его для трафика приложения можно только как отдельный платный провайдер.

## 9. Тесты

`backend/tests` — pytest с PostgreSQL-базой `dnd_test` (по умолчанию
`postgresql+psycopg://dnd:dnd@localhost:5433/dnd_test`). Фикстуры создают схему,
включают pgvector, очищают таблицы, подменяют LLM, embeddings и кубик.
Покрыты: auth, characters, создание кампании со вступлением, авто-намерение поиска,
идемпотентность без повторного броска, политика контента и безопасные перенаправления,
память, rate limit, security, config (включая блокировку OpenCode Go).
Реальный ключ модели для тестов не нужен. Alembic-миграции проверяются отдельно
(`uv run alembic upgrade head`), потому что pytest создаёт схему из metadata.

## 10. Известные ограничения (на 2026-11-17)

- Политика контента — best-effort эвристики без внешнего moderation API. Сложные
  формулировки могут пройти, а широкие правила — иногда задеть обычное фэнтези.
  Отдельная локальная модель-модератор не внедрена: сначала нужен замер памяти,
  задержки и качества на конкретном оборудовании.
- DC автоматического поиска фиксирован (15). Для сценарных DC и скрытых угроз потребуется
  структурированное состояние сцены, которого пока нет.
- CI добавлен в `.github/workflows/ci.yml`, но видимость репозитория и доступность
  GitHub Actions не проверены локально. Если Actions недоступны, обязательны ручные
  прогоны ruff/pytest/npm lint/build перед слиянием в `main`.
- Формального стандарта сообщений коммитов нет.
- `backend/data/srd/srd-5.2.1.md` — данные, а не документация: не читать целиком.
