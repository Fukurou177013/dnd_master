# С чего начать

## Что делает приложение

D&D Master — это сайт, где человек создаёт аккаунт, персонажа и кампанию, а затем
пишет мастеру в чате. «Мастер» состоит из двух частей, как команда из судьи и
рассказчика:

- Сервер — судья. Он проверяет, кто вошёл, кому принадлежат персонаж и кампания,
  решает, нужна ли проверка, бросает виртуальный кубик и считает результат.
- Языковая модель — рассказчик. Она описывает сцену и последствия понятным языком,
  используя переданные ей данные и найденные правила.

Рассказчик не должен сам менять результат кубика, придумывать сложность проверки
или выдавать выдуманное правило D&D за настоящее. Это главный принцип проекта:
игровая механика считается программой на сервере, а не моделью и не браузером.
Кубики — и для проверок в чате, и для генерации характеристик персонажа — бросает
сервер.

## Представьте театр

Удобно представить приложение как небольшой театр:

- Браузер — зрительный зал и касса: пользователь нажимает кнопки и видит результат.
- Frontend — сцена и декорации: экран, формы, список кампаний и чат.
- Backend — закулисье: проверяет билеты, исполняет правила игры и координирует работу.
- База данных — архив театра: хранит пользователей, персонажей, кампании и сообщения.
- Языковая модель — актёр-импровизатор: говорит текст по заданным правилам, но не
  распоряжается архивом и не решает, выпал ли успех на кубике.
- SRD — справочник правил, из которого сервер находит подходящие отрывки для актёра.

Это только аналогия. Технически браузер и сервер обмениваются HTTP-запросами,
а база данных отвечает на запросы backend.

## Как читать примеры

- **Сейчас** означает поведение, предусмотренное текущими кодом и архитектурой.
- **Ограничение** означает, что приложение этого пока не делает.
- **Рекомендация** означает возможный будущий шаг, а не уже реализованную возможность.
- Пути вроде `backend/app/services/game_master.py` — адреса файлов относительно корня
  репозитория, то есть главной папки проекта.
- Примеры адресов `localhost` относятся к компьютеру, на котором запущено приложение.

# Часть 1. Из чего состоит проект

## 1.1. Четыре основных участника

| Участник | Простое объяснение | Техническая роль и адрес разработки |
|---|---|---|
| Браузер | Окно, которым пользуется игрок | Показывает frontend на `http://localhost:5173` |
| Frontend | Видимая часть сайта | React и TypeScript; отправляет запросы к серверу |
| Backend | Невидимая часть с правилами и проверками | Python и FastAPI на `http://localhost:8000` |
| База данных | Надёжный архив приложения | PostgreSQL; с компьютера подключаются к `localhost:5433` |
| Языковая модель | Программа, создающая текст | Ollama или другой совместимый сервис; адрес задаётся настройкой |

**Frontend** (фронтенд) — всё, что работает для показа сайта пользователю.
**Backend** (бэкенд) — серверная часть, которая выполняет важную логику и имеет доступ
к базе данных. Это разделение похоже на ресторан: посетитель выбирает блюда в меню,
но не заходит на кухню и не меняет продукты в кладовой.

**Порт** — номер входа в программу, которая работает на компьютере. Как разные двери
в здании, номера позволяют одновременно запустить несколько программ. В разработке
сайт занимает порт 5173, backend — 8000, база данных — 5433.

**`localhost`** означает «этот же компьютер». Например, `localhost:8000` — порт 8000
на вашем компьютере, а не адрес в интернете.

**Docker** здесь запускает PostgreSQL в отдельном контейнере. Он не запускает сайт,
backend или языковую модель. Поэтому работающий Docker ещё не означает, что чат открыт.

## 1.2. Как части разговаривают

```text
Игрок
  │ нажимает кнопку или пишет сообщение
  ▼
Браузер: React-интерфейс на localhost:5173
  │ HTTP-запрос с JSON и cookie сессии
  ▼
Vite: сервер разработки и пересылка адресов /api
  │ передаёт запрос дальше
  ▼
FastAPI backend на localhost:8000
  ├── проверяет пользователя и права доступа
  ├── читает/сохраняет данные в PostgreSQL + pgvector
  └── при необходимости обращается к языковой модели
  │ возвращает JSON с результатом
  ▼
Браузер показывает сообщение, бросок, источники и память кампании
```

**HTTP** — распространённый способ отправлять запросы между программами. Запрос
говорит, что нужно сделать, например получить список или отправить сообщение.
Ответ содержит результат и код состояния: например, `200` означает успех, а `404` —
«не найдено».

**HTTPS** — защищённый вариант HTTP, который шифрует данные между браузером и сервером.
**URL** (Uniform Resource Locator) — полный адрес ресурса, например
`http://localhost:8000/health`.

**Vite** — инструмент, который во время разработки отдаёт frontend браузеру. Его
настройка пересылает запросы `/api` на backend. Для браузера сайт при этом выглядит
как единое место. Это важно для cookie входа.

**JSON** (JavaScript Object Notation) — простой текстовый формат записи данных парами
«название поля — значение». Например:

```json
{
  "content": "Я прислушиваюсь.",
  "client_message_id": "player-action-123"
}
```

Браузер отправляет JSON, сервер проверяет поля, а затем тоже возвращает JSON.
**Markdown** — обычный текст с простыми знаками оформления. Например, строка,
начинающаяся с `##`, считается заголовком второго уровня. Формат удобно читать и людям,
и программам.
**JSONL** (JSON Lines) — файл, в котором каждая отдельная строка является своим
JSON-объектом. Это удобно для большого списка отрывков: не нужно помещать их все в один
огромный массив.

# Часть 2. Что происходит при работе игрока

## 2.1. Регистрация и вход

1. Игрок отправляет email и пароль через страницу регистрации.
2. Сервер проверяет поля и превращает пароль в специальный необратимый отпечаток.
3. При входе сервер сравнивает введённый пароль с отпечатком.
4. Если пароль верен, сервер выдаёт случайный токен сессии.
5. Браузер сохраняет токен в cookie и автоматически прикладывает её к последующим
   обращениям.
6. В базе хранится не сам токен, а его SHA-256-отпечаток. При запросе сервер заново
   вычисляет отпечаток токена из cookie и ищет совпадение.

**Хеш** — результат одностороннего преобразования строки. Его можно сравнивать, но
обычно нельзя обратить обратно в исходный пароль. Для паролей используется Argon2id,
а для токена сессии — SHA-256.

**Argon2id** — современный способ хранить пароль так, чтобы подбор перебором был
дорогим по времени и памяти. Пароль в открытом виде база не хранит.

**Cookie** — маленькие данные, которые браузер хранит и отправляет серверу при
последующих обращениях. `session_token` — название cookie сессии.

Флаг **httpOnly** запрещает обычному JavaScript-коду страницы читать cookie. Это
снижает риск кражи сессии вредоносным скриптом, но само по себе не заменяет другие
меры безопасности.

Флаг **Secure** разрешает отправлять cookie только по защищённому HTTPS-соединению.
**SameSite** управляет тем, отправляется ли cookie при переходах с другого сайта.
Значение `lax` подходит для типичного веб-сценария. Значение `none` требует `Secure`,
иначе современные браузеры отклоняют cookie.

Сессия действует ограниченное время (по умолчанию 30 дней), после выхода запись
удаляется, а cookie стирается. Backend не должен отдавать пароль, его хеш или токен
клиенту и не должен записывать секреты в журналы.

## 2.2. Защита доступа

**Аутентификация** отвечает на вопрос «кто вошёл?». В этом проекте ответ даёт cookie
сессии. **Авторизация** отвечает на вопрос «что этому пользователю разрешено?». Перед
чтением кампании сервер проверяет её владельца.

Если запросить чужого персонажа или чужую кампанию, сервер отвечает `404` («не найдено»),
а не сообщает прямо, что объект существует, но принадлежит кому-то другому.

Для запросов, меняющих данные (`POST`, `PUT`, `PATCH`, `DELETE`), backend проверяет
заголовок **Origin** — адрес страницы, откуда браузер отправил запрос. Чужой адрес
получает `403`. Это одна из защит от **CSRF** (Cross-Site Request Forgery, подделка
межсайтового запроса): попытки чужого сайта заставить браузер действовать от лица
вошедшего пользователя.

**CORS** (Cross-Origin Resource Sharing, правила запросов между разными источниками)
определяет, каким сайтам браузер разрешает обращаться к API. Источник, или **origin**,
состоит из схемы (`http`/`https`), имени компьютера и порта. Например,
`http://localhost:5173` и `http://localhost:8000` — разные origin, потому что порты
различаются. В разработке Vite проксирует `/api`, поэтому браузер видит единый адрес.
Если frontend запущен отдельно, его адрес нужно явно добавить в `CORS_ORIGINS`.
Символ `*` запрещён: API использует cookie, а неограниченный список источников здесь
небезопасен.

## 2.3. Один ход в чате: пошагово

Игрок пишет, например, «Я прислушиваюсь у двери».

1. `CampaignChatPage.tsx` собирает сообщение и уникальный `client_message_id`.
2. `api.ts` отправляет запрос с `credentials: "include"`, то есть вместе с cookie.
3. Vite передаёт адрес `/api/v1/...` серверу FastAPI на порту 8000.
4. Middleware в `main.py` проверяет источник изменяющего запроса.
5. `get_current_user` в `api/deps.py` проверяет cookie и находит текущего пользователя.
6. API проверяет, что кампания и персонаж принадлежат этому пользователю.
7. Проверяется ограничение частоты запросов: обычно не больше 30 сообщений в минуту.
8. Сервер распознаёт намерение сообщения. Явный поиск может привести к проверке;
   обычное наблюдение — нет.
9. Текст проверяется политикой контента. Если сработал запрет, модель не вызывается,
   а сохраняется безопасный ответ-перенаправление.
10. Перед обычным ответом сервер ищет подходящие фрагменты SRD.
11. Сервер составляет запрос модели: инструкции, сведения персонажа, пожелание кампании,
    резюме, распознанное намерение, результат проверки, если она была, фрагменты правил
    и недавнюю историю.
12. Модель возвращает текст. Сервер ещё раз проверяет ответ по политике контента.
13. Ответ мастера и сведения о броске/источниках сохраняются в базе.
14. После успешного хода запускается фоновое обновление резюме.
15. Браузер отображает обе реплики, бросок и найденные источники.

**Middleware** — промежуточный слой, который выполняется до основного маршрута.
**API** (Application Programming Interface, программный интерфейс) — набор адресов
и правил, по которым программы обмениваются данными. Например, адрес списка кампаний
является частью API.

## 2.4. Адреса API и ответы

Все основные адреса начинаются с `/api/v1`. `v1` — номер версии интерфейса для программ.

При создании кампании браузер отправляет название, идентификатор своего персонажа и
необязательное `premise` (пожелание до 500 символов). Сервер сначала проверяет владельца
персонажа и пожелание, затем просит модель написать вступление. Если пожелание
заблокировано, ответ `422` и кампания не появляется. Если модель недоступна, ответ
`503`/`504` и кампания тоже не появляется.

При создании персонажа (`POST /characters`) браузер обязательно передаёт
`ability_score_method` — один из четырёх способов получения характеристик — и
`background_ability_bonus` — распределение бонуса от предыстории. Запрос
`PATCH /characters/{id}` принимает эти поля необязательно, но не позволяет передать `null`.
Каталог способов, их ограничения и стоимости приходит с сервера в ответе
`GET /rules/character-options`; все правила проверяет backend. Подробнее — в разделе 3.3.

Для сообщения в чат браузер отправляет текст (от 1 до 4000 символов) и необязательный
`client_message_id` длиной до 64 букв, цифр, дефисов или подчёркиваний. Поля `check`
в запросе больше нет: решение о поисковой проверке принимает backend. Например:

```json
{
  "content": "Я обыскиваю сундук.",
  "client_message_id": "chest-search-17"
}
```

Сокращённый пример ответа:

```json
{
  "user_message": {
    "role": "user",
    "content": "Я обыскиваю сундук.",
    "sequence": 2
  },
  "assistant_message": {
    "role": "assistant",
    "content": "Ты замечаешь потайное отделение.",
    "roll": {"d20": 14, "total": 16, "dc": 15, "success": true},
    "sources": []
  },
  "memory_update_scheduled": true
}
```

Реальный ответ также включает уникальные идентификаторы и время создания. `sources`
содержит найденные отрывки, если они есть. `memory_update_scheduled` — ответ на вопрос,
поставили ли фоновое обновление памяти в очередь, а не готовое резюме.

| Метод и адрес | Назначение |
|---|---|
| `POST /auth/register` | Создать аккаунт; успешный код `201` |
| `POST /auth/login` | Войти и получить cookie |
| `GET /auth/me` | Узнать, кто вошёл |
| `POST /auth/logout` | Выйти; успешный код `204` |
| `GET /characters` | Получить своих персонажей |
| `POST /characters` | Создать персонажа |
| `GET /characters/{id}` | Получить персонажа |
| `PATCH /characters/{id}` | Изменить персонажа |
| `DELETE /characters/{id}` | Удалить персонажа |
| `GET /rules/character-options` | Получить каталог вида, класса, предыстории, навыков и способов генерации характеристик |
| `POST /rules/ability-scores/roll` | Серверный бросок 4d6 без худшего кубика для шести характеристик |
| `GET /campaigns` | Получить свои кампании |
| `POST /campaigns` | Создать кампанию и её вступительную сцену |
| `GET /campaigns/{id}` | Получить кампанию и память |
| `DELETE /campaigns/{id}` | Удалить кампанию |
| `GET /campaigns/{id}/messages?limit=` | Получить историю; по умолчанию 100, максимум 500 |
| `POST /campaigns/{id}/messages` | Отправить игрока на ход мастера |

`{id}` — место, куда подставляется идентификатор конкретного объекта. `GET` обычно
читает, `POST` создаёт или отправляет, `PATCH` частично меняет, `DELETE` удаляет.

Основные коды ответа:

| Код | Человеческий смысл |
|---|---|
| `200` | Всё успешно, данные возвращены |
| `201` | Новый объект создан |
| `204` | Успешно, но возвращать тело ответа не нужно, например при выходе |
| `401` | Нет действующей сессии; нужно войти |
| `403` | Источник запроса запрещён проверкой Origin |
| `404` | Объект не найден или принадлежит другому пользователю |
| `409` | Например, email уже зарегистрирован |
| `422` | Поля запроса не прошли проверку или пожелание кампании не разрешено |
| `429` | Слишком много запросов за короткое время |
| `503` | Провайдер временно недоступен; при ходе сообщение игрока уже сохранено |
| `504` | Провайдер не ответил вовремя; при ходе сообщение игрока уже сохранено |

При создании кампании ошибка модели имеет особенность: вступление ещё не создано,
поэтому кампания не сохраняется, а повторить можно весь запрос. При ходе уже существующей
кампании сообщение игрока сохраняется до вызова модели, поэтому повтор безопасен.

# Часть 3. Данные и база

## 3.1. Что такое база данных

База данных — это организованный электронный архив. Данные разложены по **таблицам**,
похожим на таблицы в электронной книге. Столбцы задают вид сведений, строки хранят
конкретные записи.

**SQL** (Structured Query Language, язык запросов к базе) — язык, на котором можно
попросить базу найти или изменить записи. SQLAlchemy помогает составлять SQL из объектов
Python. **Модель** в папке `models/` описывает, какому набору полей соответствует таблица.

| Таблица | Что хранит |
|---|---|
| `users` | Email в нижнем регистре, имя, активность аккаунта и Argon2-хеш пароля |
| `sessions` | Хеш токена сессии, срок действия, браузер пользователя (user-agent) и IP-адрес подключения |
| `characters` | Имя, уровень, вид, класс, предысторию, характеристики и данные персонажа (метод генерации, бонус предыстории, производные значения) |
| `campaigns` | Владельца, персонажа, название, пожелание и даты кампании |
| `campaign_memories` | Одну структурированную память на кампанию в JSONB |
| `campaign_messages` | Реплики игрока и мастера, порядок и дополнительные данные |
| `srd_chunks` | Отрывки SRD, их названия, источник, лицензию и векторы смысла |
| `alembic_version` | Служебную информацию о применённых изменениях схемы |

Email пользователя хранится в нижнем регистре и уникален: например, варианты адреса,
отличающиеся только заглавными буквами, не должны создавать два отдельных аккаунта.

**UUID** (Universally Unique Identifier) — длинный уникальный идентификатор записи.
Вместо простого числа 7 у персонажа есть уникальная строка-идентификатор; так сложнее
случайно перепутать объекты разных пользователей.

У персонажа числовые характеристики хранятся в базе с возможным диапазоном 1–30,
но приложение проверяет базовые значения 3–18, а итоговые значения с бонусом
предыстории — не выше 20; уровень 1–20. Значения HP (Hit Points, хиты/запас здоровья),
AC (Armor Class, класс брони) и скорость вычисляются или проверяются сервером, поэтому
нельзя доверять подставленному браузером значению. Произвольные дополнительные сведения
хранятся в поле `data` (JSONB): там же лежат способ генерации характеристик, бонус
предыстории и все производные значения.

**JSONB** — двоичный формат JSON в PostgreSQL. Он хранит набор именованных полей,
например список навыков или резюме кампании, внутри записи базы.

Для важных связей база использует **внешний ключ** (foreign key): например, персонаж
ссылается на пользователя, а сообщение — на кампанию. Если владелец или кампания
удаляются, связанные записи могут удаляться каскадно. **Уникальное ограничение** не
позволяет сохранить две записи с одинаковой комбинацией выбранных полей.

## 3.2. Сообщения и память

У каждого сообщения есть роль (`user` — игрок, `assistant` — мастер), текст, время
создания и порядковый номер `sequence`. Уникальное ограничение не даёт двум сообщениям
одной кампании получить одинаковый номер.

В metadata (дополнительных метаданных) сообщения могут сохраняться распознанное
намерение, бросок, источники, ссылка ответа мастера на реплику игрока и отметка
о вступительной сцене. Это дополнительные сведения, не основной текст сообщения.

Резюме кампании — JSON с пятью списками:

```json
{
  "facts": ["установленные факты"],
  "goals": ["цели персонажа и группы"],
  "npcs": ["важные NPC"],
  "locations": ["важные места"],
  "open_threads": ["незаконченные события и вопросы"]
}
```

**NPC** (Non-Player Character) — неигровой персонаж, которым управляет мастер, а не
участник-игрок. Резюме — это краткая помощь памяти, а не точная карта мира. Оно не
хранит отдельным структурированным способом точное положение героя, видимые предметы,
выходы из комнаты и очередь боя.

## 3.3. Как сервер собирает карточку персонажа

Варианты вида, класса, предыстории, навыков и характеристик берутся из серверного
каталога, а не из списка, которому можно без проверки доверять в браузере. Сейчас в
каталоге есть ограниченный стартовый набор видов, классов и предысторий. Для каждого
класса заданы игровые кости хитов, допустимые навыки и спасброски; предыстория даёт
свои навыки и три характеристики для бонуса; для каждого вида указаны скорость и
дальность тёмного зрения. За каталогом обращаются по адресу
`GET /rules/character-options`.

**Характеристики** — Сила, Ловкость, Телосложение, Интеллект, Мудрость и Харизма.
Базовые значения лежат в диапазоне 3–18, а итоговые — после бонуса предыстории —
не выше 20. Уровень персонажа — 1–20. Сервер сверяет вид, класс, предысторию и навыки
с каталогом и не принимает навык, который не положен выбранной комбинации.

Способ получения шести характеристик обязательно указывается при создании персонажа
(поле `ability_score_method`) и сохраняется в `data.ability_score_method`. Каталог
описывает четыре способа, а все проверки выполняет сервер:

- **Вручную** (`manual`): игрок задаёт шесть базовых значений от 3 до 18.
- **Стандартный массив** (`standard_array`): нужно ровно шесть значений 15, 14, 13,
  12, 10 и 8, распределённых по характеристикам без повторов.
- **Покупка очков** (`point_buy`): каждое базовое значение от 8 до 15, а сумма
  стоимостей — не больше 27. Стоимость берётся из каталога: 8 стоит 0 очков, 15 — 9.
- **Бросок 4d6** (`roll_4d6`): для каждой характеристики сервер бросает четыре
  шестигранных кубика и отбрасывает худший. Бросок делает отдельный адрес
  `POST /rules/ability-scores/roll`, а не браузер; страница лишь показывает
  готовые значения и отправляет их обратно при сохранении.

**Бонус предыстории** (`background_ability_bonus`) — объект вида «характеристика →
число от 0 до 2». Предыстория разрешает бонус только трём своим характеристикам и
только в одной из двух форм: `+2` и `+1` либо `+1`, `+1` и `+1`. При создании поле
обязательно; при изменении листа его можно передать заново. Сервер складывает базовое
значение с бонусом, получая итоговое, а при проверке метода, наоборот, вычитает бонус,
чтобы сверить именно базовые значения. Присланные `strength`…`charisma` считаются уже
итоговыми.

Старые записи без `data.ability_score_method` и без `data.background_ability_bonus`
считаются legacy (унаследованными): им разрешают менять имя, заметки, уровень и текущие
хиты, но изменить характеристики без явного указания метода нельзя.

Часть значений сервер рассчитывает сам, а не считает присланное значение клиента
истиной. Все они складываются в `data` (JSONB):

- модификатор характеристики: `(значение - 10) // 2`;
- бонус владения: `2 + (уровень - 1) // 4`;
- максимум HP рассчитывается по кости хитов класса, уровню и модификатору Телосложения;
- AC в текущем упрощённом расчёте — `10 + модификатор Ловкости`;
- скорость и дальность тёмного зрения берутся из каталога выбранного вида;
- модификаторы навыков и спасбросков получают бонус владения, если персонаж обучен;
- инициатива равна модификатору Ловкости;
- пассивное Восприятие равно `10 + модификатор Восприятия`.

**Спасбросок** — проверка, помогающая сопротивляться опасности или эффекту. **Инициатива**
в D&D определяет порядок действий в бою. **Тёмное зрение** позволяет видеть в темноте
на указанное число футов; у видов без него каталог возвращает 0. Эти значения уже можно
вычислить для карточки, но это ещё не означает, что в приложении есть полный боевой движок.

Лист можно вести и после создания: интерфейс показывает карточку, даёт отредактировать
её через `PATCH /characters/{id}` (имя, заметки, уровень, вид, класс, предысторию,
навыки и характеристики), а кнопками «−» и «+» — нанести урон или полечить. При
повышении уровня пересчитываются максимум HP и бонус владения, но текущие хиты
остаются прежними. Сервер — источник истины: после каждого изменения интерфейс берёт
производные значения из ответа, а не вычисляет их заново в браузере.

## 3.4. Создание кампании и сообщения

Создание кампании сейчас генерирует вступительную сцену по персонажу и необязательному
пожеланию `premise` (до 500 символов: например, тон, жанр или сеттинг). Кампания,
пустая память и вступительное сообщение сохраняются вместе. Если сцена не получилась,
кампания не создаётся. Сцена должна быть длиннее 80 символов и пройти проверку контента;
если генерация не удалась, сервер возвращает `503` или `504`, а кампанию не сохраняет.
Ответ мастера на обычный ход ограничен снизу 1200 токенами генерации; вступление — тоже
минимум 1200. Это нужно, чтобы модель не обрывала текст из-за слишком низкой настройки
общего лимита.

**Транзакция** — группа операций с базой, которая рассматривается как единое целое:
успешно применить вместе или не оставлять половину изменений. Например, при создании
кампании нельзя сохранить кампанию без обязательного первого сообщения, если создание
вступления завершилось ошибкой.

## 3.5. Миграции схемы

Схема — это устройство таблиц и их столбцов. **Миграция** — записанный в файле шаг,
который меняет схему с одной версии на следующую. В проекте миграции управляются
Alembic и находятся в `backend/alembic/versions/`.

Изменить Python-модель недостаточно: установленная база от этого сама не перестроится.
Нужно создать и проверить миграцию. Команда `uv run alembic upgrade head` применяет
все изменения до самой новой версии (`head`). Команда `uv run alembic current`
показывает применённую базой версию.

Размерность вектора SRD равна 1024: настройка `LLM_EMBEDDING_DIMENSIONS` и столбец
`vector(1024)` должны совпадать. При смене размера нужно поменять код/схему, создать
миграцию и построить embeddings заново. Старые векторы другой длины нельзя просто
пересчитать на месте. В частности, откат миграции размерности очищает таблицу SRD,
потому что преобразовать векторы обратно корректно нельзя.

Расширение листа персонажа схему таблиц не меняло: способ генерации характеристик
и бонус предыстории хранятся внутри уже существовавшего поля `data` (JSONB), поэтому
отдельная миграция для них не потребовалась.

# Часть 4. Как мастер использует языковую модель и правила

## 4.1. Модель — не весь мастер

**LLM** (Large Language Model, большая языковая модель) — программа, которая создаёт
текст, продолжая входное описание. В проекте это внешний по отношению к коду сервис.
Им может быть локальная Ollama или другой сервер с совместимым API.

Модель не держит полную память игры самостоятельно. На каждом новом запросе backend
передаёт ей нужные данные заново. Так проще контролировать, что именно модель знает.

В проекте «мастер» — это три вещи:

1. Python-код: проверяет игрока, делает броски, ищет правила и сохраняет журнал.
2. Системная инструкция: задаёт модели роль, стиль и границы.
3. LLM: пишет текст сцены и последствий на основании полученного контекста.

Модель может ошибиться или нарушить текстовую инструкцию. Поэтому важные ограничения
нельзя поручать только просьбе в prompt: правила игры считает код.

## 4.2. Prompt: рабочая папка модели

**Prompt** — весь текст и набор сообщений, отправляемых модели для одного ответа.
Представьте, что перед актёром каждый раз кладут папку с ролью, кратким пересказом,
справочником и предыдущими репликами. Актёр знает только то, что есть в этой папке.

Для обычного хода папка примерно содержит:

```text
1. Системная инструкция: как отвечать и чего не делать.
2. Краткое резюме кампании.
3. Намерение игрока: наблюдение, неоднозначный поиск или проверка поиска.
4. Готовый результат проверки, если сервер её выполнил.
5. Найденные фрагменты SRD, если они нашлись.
6. Данные персонажа и пожелание кампании, обозначенные как недоверенные данные.
7. До 12 последних сообщений истории.
```

Контекст персонажа включает имя, вид, класс, предысторию, уровень, владение навыками
и пассивное Восприятие, если оно есть в данных. При этом не каждое поле листа
включается: например, HP и все числа не передаются как полный лист. Пожелание кампании
и текст игрока помечаются как недоверенные сведения: они не могут менять системные
правила модели.

Системная инструкция требует отвечать по-русски, кратко и атмосферно, примерно в
2–4 абзацах для обычного хода; вступление — в 3–5 абзацах. Модель может создавать
атмосферу, места, NPC и события вымышленного мира. Правила D&D она должна подтверждать
найденными фрагментами SRD, не придумывать кубики и не менять результат сервера. Если
источников недостаточно, нельзя выдавать придуманное правило за факт. Если намерение
неясно, модель должна задать вопрос. Ответ не должен раскрывать системные инструкции.

Для Ollama в конфигурации можно добавить к системной инструкции специальный суффикс.
В частности, `/no_think` для некоторых моделей Qwen просит не показывать/не тратить
время на развёрнутый режим рассуждения. Для иных моделей такой суффикс может не
подходить. Установленный суффикс задаётся настройкой `LLM_SYSTEM_SUFFIX`.

**Токен** в настройке модели — условная единица текста, примерно кусочек слова или
знак пунктуации. Это не обязательно целое слово. Лимит токенов ограничивает длину
генерации. **Температура** регулирует разнообразие: низкая делает ответы более
однообразными и предсказуемыми, высокая — более вариативными. Это не оценка качества.

## 4.3. SRD: справочник правил

**SRD** (System Reference Document) — открытый справочный документ с частью правил
D&D. В этом проекте используется SRD 5.2.1 под лицензией CC BY 4.0. **CC BY 4.0** —
лицензия Creative Commons Attribution 4.0: она разрешает пользоваться материалом при
соблюдении условия об указании авторства/источника.

Текст корпуса SRD не хранится в Git. Его нужно отдельно положить в `backend/data/srd/`
и импортировать. Скрипт понимает два формата:

- Markdown или обычный текст с заголовками от `#` до `######`;
- JSONL — текстовый файл, где каждая строка является отдельным JSON-объектом с полями
  `section`, `title`, `content`, а также необязательными `source`, `license`, `metadata`.

При импорте:

- максимальный размер отрывка — 1600 символов;
- короткий отрывок (меньше 200 символов) может присоединиться к предыдущему в том же
  разделе;
- длинный абзац делится на части;
- для Markdown сохраняется путь заголовков, например `Using Ability Scores / Ability Checks`;
- для поиска вектор строится из названия раздела, заголовка и текста;
- запросы к модели embedding отправляются пачками по 32 отрывка.

**Импорт** — загрузка и подготовка корпуса в базу. Для каждого отрывка вычисляется
SHA-256-ключ из источника, раздела и текста. Если отрывок уже загружали, повторный
импорт его пропустит и не создаст копию. Это пример идемпотентности.

В таблице хранятся источник, раздел, заголовок, текст, лицензия, метаданные и embedding.
В метаданных могут лежать URL источника, имя файла и путь заголовков. В ответ API
передаются идентификатор, источник, раздел, заголовок, лицензия и короткая выдержка,
а не весь текст. Полный текст доступен самой модели только внутри запроса, где отрывок
обрезается до 1800 символов.

У каждого отрывка есть `chunk_key` — уникальный ключ, предотвращающий повторную вставку.
Для поиска PostgreSQL сортирует результаты по косинусному расстоянию; при одинаковом
расстоянии порядок дополнительно стабилизируется по идентификатору записи. HNSW — индекс
для ускорения этого поиска, а не отдельная модель и не источник новых правил.

## 4.4. Embedding и поиск похожего смысла

**Embedding** (эмбеддинг, векторное представление) — набор чисел, который кодирует
смысл текста. Например, фразы «идти в таверну» и «зайти в трактир» могут иметь близкие
векторы, даже если их слова различаются.

**Вектор** — последовательность чисел. PostgreSQL с расширением pgvector хранит векторы
в специальном типе `vector(1024)`. При каждом поиске отдельная embedding-модель превращает
сообщение игрока в такой вектор. База сравнивает его с векторами отрывков SRD и выбирает
четыре ближайших по смыслу.

Для сравнения используется **косинусное расстояние**. Представьте стрелки на плоскости:
чем меньше угол между стрелками, тем ближе направления и тем больше смысловое сходство.
В базе включён индекс **HNSW** (Hierarchical Navigable Small World, «иерархический
навигаемый малый мир») — структура, помогающая быстро искать приблизительно близкие
векторы, не сравнивая каждый отрывок самым медленным способом.

**Retrieval** — этап поиска подходящих документов. **RAG** (Retrieval-Augmented
Generation, генерация с поиском) — подход, где сначала находят материалы, затем
вкладывают их в prompt модели. В этом проекте retrieval ищет отрывки SRD, а модель
пишет ответ с учётом этих отрывков.

Текущие границы поиска:

- берутся четыре лучших совпадения (настройка `RETRIEVAL_TOP_K`);
- порога качества нет: даже не очень похожий текст может попасть в четвёрку;
- нет второго этапа, который заново сортирует найденные отрывки;
- нет отдельного буквального поиска по словам;
- запрос не переписывается с синонимами;
- если корпус пустой, модель получает указание не выдумывать правила;
- если embedding-провайдер недоступен, ход может продолжиться без источников;
- если ошибка возникла непосредственно в базе, она не обязательно превращается в
  «ответ без источников» и может привести к ошибке сервера;
- в карточке источника API показывает excerpt максимум 400 символов.

`top-k` — короткое название операции «оставить k лучших совпадений»: здесь `k = 4`.

Поиск по смыслу полезен, но не гарантирует, что найден правильный раздел. Модель тоже
может неверно истолковать текст. Поэтому наличие ссылки — не абсолютная гарантия
правильного ответа.

## 4.5. Два слоя памяти кампании

1. **Полный журнал сообщений.** Сохраняет реплики с порядковыми номерами. В интерфейсе
   можно запросить от 1 до 500 сообщений, по умолчанию 100.
2. **Структурированное резюме.** Пять списков фактов, целей, NPC, мест и незавершённых
   событий. Оно помогает модели не забывать важное, но не заменяет полный журнал.

После успешного ответа мастера сервер ставит фоновую задачу обновить резюме:

1. Задача открывает отдельное подключение к базе.
2. Берёт старое резюме и недавние сообщения (по умолчанию 12).
3. Просит модель вернуть только JSON с той же структурой.
4. Проверяет форму результата схемой `CampaignSummary` и сохраняет его.
5. Если провайдер недоступен, ответ невалиден или задача упала, старое резюме остаётся.

Вызов для резюме использует температуру 0.2 и лимит до 1500 токенов. Ошибка обновления
не отменяет уже сохранённый ход. Поле `memory_update_scheduled: true` значит только
«задача поставлена в очередь»; это не доказательство, что резюме уже обновилось.
Фоновая задача может не завершиться, если процесс приложения сразу остановить.
Задача обрезает слишком длинные тексты истории до 1500 символов перед передачей модели.
Если сообщение игрока было заблокировано политикой, оно пропускается при обновлении
резюме, чтобы опасный текст не попадал туда повторно.

## 4.6. Почему повтор отправки безопасен

**Идемпотентность** — свойство операции, при котором повтор той же просьбы не создаёт
второй результат. У сообщения есть `client_message_id` — созданный браузером ключ
конкретной отправки. Для каждой кампании такой ключ уникален.

Если игрок повторил запрос после тайм-аута:

- если ответ мастера уже сохранён, backend вернёт ранее сохранённую пару реплик;
- если реплика игрока сохранена, но ответа ещё нет, backend продолжит с прежнего
  результата броска;
- новый бросок не выполняется и копия сообщения не создаётся.

Для сериализации одновременных ходов одной кампании используется PostgreSQL advisory
lock — блокировка, которую приложение берёт внутри транзакции. Это похоже на один
ключ от комнаты: пока один ход выполняется, второй запрос ждёт. Уникальность пары
`(campaign_id, sequence)` дополнительно защищает порядок сообщений.

Лимит частоты запросов хранится в памяти одного процесса. После перезапуска он
обнуляется. Если запустить несколько процессов или серверов, у каждого будет свой
счётчик; для единого общего счётчика нужен отдельный общий сервис, например Redis.

# Часть 5. Игровые проверки и безопасность контента

## 5.1. Как устроен бросок

**d20** — двадцатигранный кубик с результатом от 1 до 20. **Проверка** — бросок,
который помогает решить, удалось ли действие. **DC** (Difficulty Class, класс
сложности) — число, которое нужно набрать или превысить. **Модификатор** — число,
которое прибавляют к броску на основе характеристики. Навык может добавить бонус
владения, если персонаж обучен ему.

Примеры навыков: **Perception** — Восприятие (заметить или услышать), **Investigation** —
Расследование (внимательно найти или изучить следы). **Proficiency** — владение:
обученный навык даёт дополнительный бонус.

Сейчас сервер распознаёт поисковое намерение обычного текста. Это не свободный выбор
DC игроком и не решение LLM. В общих чертах:

- обычное наблюдение («что я вижу?», «осматриваюсь») не требует броска;
- явное прислушивание/высматривание может стать проверкой Восприятия;
- явный поиск тайника, следов, ловушки или обыск может стать проверкой Расследования;
- неоднозначная короткая фраза вроде «ищу» может попросить уточнение вместо броска;
- автоматическая сложность таких поисковых проверок фиксирована: DC 15.

Распознавание детерминированное: используется код и словари/шаблоны, а не случайное
решение языковой модели. Это не универсальное понимание любого текста: оно покрывает
известные формулировки и может не распознать необычное выражение.

Когда проверка определена, сервер:

1. проверяет допустимость характеристики и навыка;
2. проверяет, что навык связан с указанной характеристикой;
3. проверяет, что DC находится от 5 до 30;
4. берёт реальное значение характеристики персонажа;
5. вычисляет модификатор: `(характеристика - 10) // 2`, где `//` означает деление
   с округлением вниз до целого;
6. если персонаж владеет навыком, добавляет бонус владения:
   `2 + (уровень - 1) // 4`;
7. случайно выбирает число от 1 до 20 через криптографически надёжный генератор;
8. складывает бросок и модификатор;
9. сравнивает итог с DC: успех, если итог не меньше сложности;
10. сохраняет d20, модификатор, DC, итог, успех и владение навыком.

Например, при Мудрости 14 модификатор равен `+2`: `(14 - 10) // 2 = 2`. Если d20
показал 12, итог будет `12 + 2 = 14`. Против DC 15 это неудача, потому что 14 меньше
15. В этой упрощённой реализации для такой проверки нет отдельного правила, которое
автоматически меняет успех из-за натуральной единицы или двадцатки.

Пользователь не может сообщить серверу, что ему выпало, например, 20. Клиент посылает
только сам текст; сервер сам определяет, нужна ли автоматическая проверка, сам бросает
кубик и сохраняет результат. Результат передаётся модели как факт, который нельзя
менять.

Пока нет преимущества и помехи, критических успехов/провалов, боевого движка, оружия,
брони как боевой системы, заклинаний и инвентаря. Также нет полной автоматизации
каждого возможного вида проверки. Это упрощённый серверный поиск, а не полноценная
симуляция D&D.

## 5.2. Политика контента

Политика контента отвечает на вопрос, какие темы игра может продолжать. Сейчас это
best-effort (работа «насколько хорошо удаётся», без абсолютной гарантии) слой проверок
на сервере:

- пожелание кампании проверяется при её создании;
- текст игрока проверяется до обращения к модели;
- ответ модели проверяется после генерации;
- при явном срабатывании опасный текст не отправляется дальше или заменяется коротким
  безопасным перенаправлением;
- заблокированный ход записывается, но обновление резюме для такого обмена не планируется.

При заблокированном сообщении пользователя backend сохраняет саму реплику с пометкой
`policy_blocked`, не вызывает чат-модель и сохраняет безопасное перенаправление без
броска и источников. Если проверку не проходит уже сгенерированный ответ, этот ответ
заменяется тем же безопасным перенаправлением до сохранения.

Допустимы мрачное взрослое фэнтези, подходящая грубая речь, повествовательное насилие
и конфликты вымышленных групп. Запрещены сексуальный контент с несовершеннолетними,
груминг и эксплуатация, сцены насилия с несовершеннолетними, реальные призывы к
ненависти/травле/насилию и практические инструкции реального вреда или незаконных
действий. Код использует эвристические текстовые шаблоны, а не отдельную модель
модерации.

**Эвристика** — приближённое правило, которое часто срабатывает, но не понимает смысл
идеально. Поэтому сложный запрет может пройти, а безобидная фраза иногда может быть
задета. Проект не обещает абсолютную безопасность и не выполняет проверку возраста.
Отдельная локальная модель-модератор не установлена.

Текстовая инструкция в prompt — не надёжная техническая блокировка сама по себе.
Защитные решения должны выполняться кодом до и после модели. Всё, что прислал игрок,
история и пожелание кампании считаются недоверенными данными, а не командами менять
правила системы.

# Часть 6. Инфраструктура, настройки и запуск

## 6.1. PostgreSQL и Docker

**PostgreSQL** — программа для хранения структурированных данных. **pgvector** — её
расширение для числовых векторов и поиска похожего смысла. В разработке база запускается
контейнером Docker Compose из `backend/docker-compose.yml`.

**Образ** Docker — готовый шаблон программы, здесь PostgreSQL с pgvector. **Контейнер** —
запущенный экземпляр образа. **Volume** — отдельное постоянное хранилище контейнера.
База в контейнере хранит данные в volume `pgdata`: обычный перезапуск их сохраняет.
Удаление volume удаляет данные, даже если исходный код проекта остался.

В описании разработки используются PostgreSQL 17 и внешний порт 5433, направленный
на порт 5432 внутри контейнера. Стандартный 5432 часто занят локально установленной
базой, поэтому проект использует другой внешний номер. Локальные значения пользователя,
пароля и базы для контейнера описаны в `backend/docker-compose.yml`: это локальная база
`dnd` с пользователем/паролем разработки `dnd`/`dnd`. Такие простые значения допустимы
только для локальной разработки; нельзя оставлять их для публичного сервера. Не
переносите пароли в общедоступные сообщения.

Healthcheck — автоматическая проверка, готова ли база принимать запросы. В Compose она
использует `pg_isready`.

## 6.2. Ollama, провайдеры и стоимость

**Ollama** — программа, которая запускает языковые модели локально на вашем компьютере.
Её OpenAI-совместимый адрес обычно выглядит как `http://localhost:11434/v1`. «Совместимый»
значит, что формат HTTP-запросов похож на формат OpenAI; это не значит, что запрос
обязательно идёт в OpenAI.

В текущих настройках по умолчанию указаны:

- чат-модель `qwen3:14b`;
- embedding-модель `qwen3-embedding-cpu`;
- локальный адрес Ollama;
- тестовое/локальное значение ключа `ollama` для совместимого клиента.

Для локального запуска не оплачивается каждый запрос провайдеру, но нужны память,
подходящий процессор/видеокарта, электричество и место на диске. Облачные провайдеры
могут взимать плату по тарифу, поэтому фактический адрес и ключ нужно проверять в
локальной конфигурации, не публикуя секреты. Файл `backend/.env` содержит личные
настройки; этот учебник его не читает и не показывает.

**OpenAI-совместимый API** — общий формат общения с моделями. Его могут поддерживать
Ollama и разные облачные сервисы.

OpenCode Go — подписка coding-агента, а не разрешённый игровой провайдер. Политика
проекта запрещает направлять туда запросы самого приложения, backend, тестов и генерации
D&D-контента. Сейчас `config.py` при запуске отклоняет URL Go (`/zen/go` и
`/inference/go`). Обычный OpenAI-совместимый облачный сервис этой проверкой сам по себе
не запрещён, но может быть платным.

Бесплатность относится к программам и локальному запуску, а не к любым расходам.
Электричество, оборудование, интернет, серверы и CI-раннеры сверх бесплатных лимитов
могут стоить денег. Подписка coding-агента не является частью приложения.

## 6.4. Запуск и проверки

Для полноценной локальной разработки понадобятся Docker с PostgreSQL/pgvector, Python
и `uv`, Node.js и npm. Основные команды ниже записаны для PowerShell. Backend-команды
выполняются из папки `backend`, frontend-команды — из `frontend`.

Запустить базу:

```powershell
docker compose up -d db
docker compose ps
```

Установить зависимости Python:

```powershell
uv sync
```

Применить изменения схемы и посмотреть версию базы:

```powershell
uv run alembic upgrade head
uv run alembic current
```

Импортировать корпус SRD после того, как исходный файл законно получен и помещён
в ожидаемое место:

```powershell
uv run python -m app.scripts.import_srd data/srd/srd-5.2.1.md `
  --source "SRD 5.2.1" `
  --source-url "https://www.dndbeyond.com/srd" `
  --license "CC BY 4.0"
```

Запустить backend на Windows:

```powershell
uv run uvicorn app.main:app --reload --port 8000 --loop app.core.loop:selector_loop_factory
```

`SelectorEventLoop` — способ Windows обрабатывать асинхронные события. Backend и
импорт SRD используют его для совместимости с драйвером PostgreSQL. После запуска
проверка `http://localhost:8000/health` должна вернуть `{"status":"ok"}`. Страница
`http://localhost:8000/docs` показывает автоматически созданное описание API.

Запустить frontend в другом терминале:

```powershell
npm install
npm run dev
```

Если PowerShell запрещает запуск оболочки `npm`, на Windows можно использовать
`npm.cmd`.

Проверки backend:

```powershell
uv run ruff check app
uv run pytest -q
```

Проверки frontend:

```powershell
npm.cmd run lint
npm.cmd run build
```

`start.bat` из корня автоматизирует запуск базы, миграций, backend и frontend; команда
`start.bat stop` останавливает их. Он не импортирует SRD автоматически. Если отрывки
не загружены, чат может работать, но ссылки на правила будут отсутствовать. При первом
запуске скрипт создаёт `backend/.env` из безопасного шаблона и подставляет адрес локальной
базы. Для выбранного провайдера может понадобиться заполнить `LLM_API_KEY`; если ключ
пустой и провайдер требует ключ, чат ответит `503`, а сетевой запрос к модели не будет
успешным. Не показывайте содержимое `.env` другим людям.

# Часть 7. Проверки программы и её границы

## 7.1. Что проверяют автоматические тесты

Тесты запускаются через `pytest` и используют отдельную базу `dnd_test`, а не обычную
базу игры. Нужен запущенный PostgreSQL с pgvector. Реальный ключ модели для большинства
тестов не требуется: внешние зависимости заменяются тестовыми подделками.
Если тестовая база ещё не создана, тестовая настройка пытается создать её автоматически.

**Fake provider** (поддельный провайдер) — тестовая программа, которая отвечает заранее
известным текстом вместо настоящей модели. Так тест можно повторять и получать
предсказуемый результат.

- `FakeChatProvider` возвращает заданный текст мастера и резюме.
- `FakeEmbeddingProvider` возвращает заранее определённый вектор.
- `FixedRollGenerator` возвращает фиксированные результаты d20 (обычно 20) и d6
  (обычно 4), чтобы бросок 4d6 для характеристик тоже был предсказуемым.

Поэтому тест способен проверить бизнес-логику без сети и случайности. Схема тестовой
базы строится из Python-моделей через `Base.metadata.create_all`, а не миграциями Alembic.
Следовательно, тесты приложения сами по себе не доказывают, что миграции правильно
перестраивают настоящую базу. Миграции проверяют отдельной командой Alembic.

Покрываются, в том числе:

- регистрация, вход и доступ разных пользователей к своим данным;
- создание кампании и вступительная сцена;
- проверка персонажа, кампании и допустимых вариантов;
- каталог способов генерации характеристик, бюджет покупки очков, стандартный массив
  и серверный бросок 4d6;
- бонус предыстории, унаследованные записи и редактирование листа персонажа;
- распознавание поискового намерения и серверный бросок;
- SRD-источники и ход без найденных источников;
- повтор с тем же `client_message_id` без дубля и нового броска;
- поведение при недоступности или тайм-ауте модели;
- сохранение сообщения игрока после ошибки провайдера;
- безопасное перенаправление по политике контента;
- ошибка или неправильный JSON при обновлении резюме;
- лимит частоты запросов и настройки, включая блокировку Go.

## 7.2. Чего тесты не доказывают

Автоматические тесты не гарантируют:

- что конкретная локальная Ollama выдаёт хороший литературный текст;
- что все необычные фразы будут правильно распознаны как поиск;
- что политика контента не имеет ложных пропусков или срабатываний;
- что браузер выглядит удобно и доступен для всех устройств;
- что лимит общий при нескольких процессах;
- что миграции совпадают с моделями, если отдельно не применить их к базе;
- что корпус SRD установлен, свеж и качественно проиндексирован;
- что внешний провайдер не выставит счёт по своему тарифу;
- что производительность будет одинаковой на разных компьютерах.

CI (Continuous Integration, непрерывная интеграция) — автоматический запуск проверок
при отправке изменений или открытии Pull Request. В репозитории есть workflow для
backend и frontend, но локальное наличие файла не доказывает, что GitHub Actions доступен
и успешно запускается для конкретного репозитория. Поэтому важные локальные проверки
всё равно нужны.

## 7.3. Что работает и чего пока нет

| Область | Текущее положение |
|---|---|
| Аккаунт | Регистрация по email/паролю, безопасное хранение пароля, сессия-cookie |
| Персонажи | Создание и редактирование листа, четыре способа генерации характеристик, бонус предыстории, правка уровня и текущих хитов; все правила проверяет сервер |
| Кампании | Личные кампании, необязательное пожелание и генерируемое вступление |
| Журнал | Реплики игрока/мастера и безопасные повторы запросов |
| Поиск правил | SRD через embeddings и pgvector; результат зависит от загруженного корпуса |
| Игровая проверка | Серверный поиск намерения; автоматический поисковый DC равен 15 |
| Резюме | Фоновое структурированное обновление пяти списков |
| Политика контента | Серверные best-effort проверки до и после LLM |
| Email | Нет подтверждения email и восстановления пароля |
| Совместная игра | Кампания принадлежит одному пользователю, совместных игроков нет |
| Полное состояние сцены | Нет отдельной подробной модели мира, видимых предметов и точной позиции |
| Полный лист персонажа в prompt | Передаются некоторые сведения, но не весь лист и не все числа |
| Боевая система | Нет полноценного боя, инициативы по раундам, оружия, заклинаний и инвентаря как системы |
| Преимущество/помеха | Не реализованы |
| Возраст | Нет проверки возраста пользователя |
| Модератор-модель | Отдельная локальная модель модерации не внедрена |
| Поиск по истории | Нет поиска по старым сообщениям |
| Стриминг | Модельный ответ показывается целиком после генерации |
| Стоимость токенов | Интерфейс не показывает расход по кампании |
| Общий лимит запросов | Счётчик живёт в памяти процесса, не общий для группы серверов |
| Улучшенный поиск | Нет порога сходства, буквального поиска и второго переранжирования |
| Production | Полная подготовка к промышленному развёртыванию не описана как завершённая |

**Стриминг** — показ ответа частями по мере генерации. Без него пользователь ждёт,
пока модель закончит ответ целиком.

## 7.4. Известные риски, о которых важно помнить

1. Поиск может передать модели нерелевантный отрывок: у него нет порога минимального
   сходства.
2. Ошибка самого провайдера embedding допускает ответ без источников, но сбой базы
   поиска может оборвать запрос.
3. Резюме обновляется в фоне. Ответ `memory_update_scheduled` не обещает, что текст уже
   сохранён в памяти.
4. Счётчик сообщений сбрасывается при перезапуске и не согласуется между процессами.
5. Фильтр контента — набор эвристик, а не доказательство полной безопасности.
6. У модели ограничен контекст: в prompt попадают последние 12 сообщений, а полная
   история доступна отдельно в интерфейсе.
7. Модель получает данные, отобранные backend. То, чего нет в prompt и памяти, она может
   не знать, даже если это где-то показывалось пользователю раньше.
8. Локальная скорость ответа зависит от модели и оборудования; одинаковая настройка на
   разных компьютерах не означает одинаковое время ожидания.
9. Настройки `.env` могут отличаться от значений по умолчанию. Никогда не публикуйте
   содержимое этого файла: в нём могут быть ключи и пароли.

| Temperature / температура | Настройка вариативности генерации модели, не температура компьютера |
| TTL | Time To Live — срок, в течение которого сессия или данные считаются действующими |
| Transaction / транзакция | Группа действий с базой, применяемая как единое целое |
| Worktree | Дополнительная рабочая папка одного Git-репозитория для отдельной ветки |

# Часть 9. Git: история и безопасная работа

## 9.1. Git простыми словами

**Git** — система, которая хранит историю изменений файлов. Можно представить её как
книгу с контрольными снимками проекта.

- **Репозиторий** — проект вместе с историей.
- **Коммит** — сохранённый набор связанных изменений с подписью.
- **Ветка** — отдельная линия изменений, чтобы работать над задачей, не меняя сразу
  стабильный вариант.
- **Remote** — удалённая копия репозитория, например на GitHub.
- **Tracking branch** — связь локальной ветки с её удалённой парой.
- **Merge** — объединение изменений из одной ветки с другой.
- **Worktree** — дополнительная папка на диске для отдельной ветки того же репозитория.
- **Pull Request (PR)** — предложение принять изменения с обсуждением и проверками.
- **CI** — автоматические проверки, запускаемые системой при изменениях.

«Структура репозитория» — где лежат папки backend и frontend. «Стратегия ветвления»
или Git workflow — как команда использует ветки и слияния. Это разные вопросы, хотя
иногда оба неформально называют Git-архитектурой.

## 9.2. Простая стратегия для небольшой команды

Рекомендация для одиночной разработки:

1. `main` — стабильная ветка с проверенным кодом.
2. Для одной задачи создать короткую feature-ветку, например
   `feature/opening-scene`.
3. Запустить нужные проверки.
4. Влить изменения в `main` напрямую или через PR, если нужно обсуждение.
5. Не держать отдельную постоянную интеграционную ветку без реальной необходимости.
6. Не сохранять пароли и ключи в Git; локальный `.env` должен оставаться вне репозитория.

Не нужно менять историю коммитов или удалять рабочие ветки только ради «чистоты».
Перед действиями с чужими или незнакомыми изменениями сначала выясните, кому они нужны.
Незакоммиченные изменения нельзя считать мусором и автоматически удалять.

**`.gitignore`** — файл с правилами, говорящими Git, какие локальные файлы не добавлять
в историю, например временные каталоги и секретные настройки. Если важный документ
случайно попал под правило игнора, это стоит проверить перед добавлением документации.

# Часть 10. Что можно улучшать дальше

Этот раздел — не обещание плана разработки. Это набор направлений, которые полезно
обсуждать после того, как текущая реализация проверена. Первые основы уже есть: локальная
конфигурация Ollama, блокировка OpenCode Go, базовые тесты, вступительная сцена,
распознавание поиска и best-effort политика контента. Ниже — возможное развитие этих
частей и оставшиеся задачи.

## 10.1. Сравнивать качество на одинаковых примерах

**Baseline** — зафиксированный набор примеров и ожидаемого поведения до изменения.
Он нужен, чтобы после правки понимать, стало лучше или хуже.

Примеры сценариев для такого набора:

- «осматриваюсь», «оглядываюсь», «прислушиваюсь», «обыскиваю комнату», «что я вижу?»;
- новая кампания с только что созданной сценой;
- пустой корпус SRD;
- недоступная embedding-модель;
- недоступная чат-модель и тайм-аут;
- повтор запроса с прежним `client_message_id`;
- неправильная пара навыка и характеристики;
- слишком длинное сообщение;
- сообщение с автоматической проверкой и без неё;
- разрешённый сюжет и фраза, которую политика должна отклонить.

Для каждого примера фиксируют ожидаемый код ответа, наличие броска/источников и факт
сохранения сообщения. Литературный ответ можно оценивать отдельно от механических
инвариантов. Качество зависит от модели, оборудования и способа сжатия модели
(квантования); время вроде «около 20 секунд» не является гарантией для каждого ПК.

Хороший порядок для такого сравнения:

1. Зафиксировать короткий список фраз, включая разные варианты одной просьбы.
2. Для каждой фразы записать ожидаемое намерение, должен ли быть бросок, ожидаемый DC,
   возможные источники и код ответа при сбое.
3. Запустить набор на обычной рабочей модели, отдельно записать текст ответа и время.
4. После изменения повторить ровно тот же набор, на той же модели и по возможности на
   том же оборудовании.
5. Сначала сравнить важные гарантии: не выдуман ли бросок, верны ли ссылки, не потеряно
   ли сообщение. Только затем сравнивать стиль рассказа.

В тестах, где проверяется именно backend-логика, продолжать применять fake-модели и
фиксированный кубик. Реальный чат-провайдер нужен для ручной оценки текста, а не для
каждого автоматического теста.

## 10.2. Улучшать понимание сцены

Сейчас есть вступительная сцена и резюме, но нет отдельного полного состояния мира.
В будущем можно хранить место, видимые объекты, выходы, NPC, время и уже найденные
детали как данные, а не только как прозу.

Полезные принципы:

- включать установленное состояние сцены в prompt;
- если место или предмет не задан, не просить модель выдавать догадку за факт;
- разделять описание мира и игровую механику;
- автоматически не назначать неизвестную проверку и не позволять LLM менять DC;
- после тестов на разных формулировках расширять распознавание, а не полагаться на
  единственный точный набор фраз;
- не хранить важное состояние только в последнем сообщении, которое может выпасть из
  контекста после длинной истории.

Критерии готовности такого изменения можно сформулировать проверяемо:

- знакомые фразы про осмотр и слух дают ответ на основе сохранённой сцены;
- если сцена не содержит конкретного объекта, ответ не утверждает, что объект точно есть;
- неоднозначная просьба вызывает короткое уточнение, а не случайную механику;
- если нужна проверка, её назначает backend, и модель получает уже готовый результат;
- результат одинаков по механике при повторной отправке одного `client_message_id`;
- сцена остаётся доступной после длинного журнала, а не только пока сообщение попадает
  в последние 12 реплик.

Не следует подменять состояние сцены списком точных фраз и не следует просить LLM
угадывать DC. Нарративная часть (что герой видит) и механическая часть (какой бросок
разрешён и что выпало) должны оставаться различимыми.

## 10.3. Развивать политику контента аккуратно

Текущие шаблоны — простой начальный слой. Возможное продолжение:

- собирать тесты разрешённых примеров и примеров, которые обязаны блокироваться;
- следить отдельно за пропусками и ложными срабатываниями;
- поддерживать безопасный ответ, который не повторяет опасную формулировку;
- подумать о локальной модели-модераторе только после замеров памяти, задержки и
  качества на целевом оборудовании;
- не заявлять абсолютную защиту и не собирать возрастные/личные данные без отдельной
  необходимости и решения о хранении.

Перед расширением стоит отдельно письменно решить границы. Например, текущая идея
разрешает уместную грубую речь, мрачное вымышленное фэнтези, повествовательное насилие
и предрассудки вымышленных групп; запрещённые примеры могут включать сексуальную
эксплуатацию несовершеннолетних, груминг, реальную ненависть и травлю, призывы к
реальному насилию, практические инструкции причинить вред и раскрытие личных данных.
Этот список — предложение для обсуждения, а не заявление, что каждое упомянутое правило
уже проверяется кодом.

До внедрения следует решить, где будет проверяться возраст (если это вообще требуется),
как не собирать лишние персональные данные, как показывать безопасный отказ, что делать
с ложными срабатываниями и каким провайдерам разрешено передавать текст. Политика в
prompt полезна, но недостаточна без проверок на сервере. Нельзя писать опасный текст
в обычные журналы просто для отладки.

Для проверки подготовить пары примеров: запрещённая формулировка прямо и обходным
языком должна безопасно блокироваться; разрешённое фэнтези не должно автоматически
запрещаться; отказ не должен раскрывать внутренние инструкции или повторять опасную
часть; после отказа игрок должен понимать, как продолжить сюжет безопасно.

## 10.4. Улучшать поиск и эксплуатацию

Возможные отдельные направления:

- добавить порог минимального сходства, чтобы далёкий отрывок не выдавался как полезный;
- совместить смысловой поиск с буквальным поиском по словам;
- проверять качество выдачи на вопросах из правил;
- сделать общий rate limiter, если приложение запускается несколькими процессами;
- добавить учёт токенов и времени ожидания без записи секретов;
- проверять миграции на отдельной базе в CI;
- подготовить документацию production-развёртывания, резервных копий и восстановления.

Не следует добавлять сложную инфраструктуру до появления конкретной необходимости.
Например, Redis полезен для общего счётчика между серверами, но не обязателен для
одного локального процесса.

Провайдер Go уже блокируется конфигурацией при старте, но полезно сохранять тесты,
проверяющие одновременно четыре случая: Go URL отклоняется; локальный Ollama URL
принимается; обычный облачный OpenAI URL не блокируется только из-за того, что он
облачный; неоднозначные URL проверяются разбором адреса, а не простым поиском слова
`go`. Это защищает запрет Go и не запрещает случайно все остальные облачные сервисы.

Для поиска улучшение следует оценивать не только по красивому ответу модели. Нужен
небольшой набор вопросов с известным правильным разделом SRD; для каждого проверяется,
попал ли нужный отрывок в top-k, насколько часто попадает нерелевантный текст и что
происходит, когда правильный источник вообще не найден. Порог сходства должен приводить
к честному ответу «не нашёл», а не к выдуманной ссылке.

## 10.5. Как проверять каждое изменение

Обычный безопасный порядок:

1. Сначала сформулировать наблюдаемое поведение, которое должно измениться.
2. Добавить/обновить тесты с fake-провайдерами и фиксированным кубиком.
3. Запустить backend Ruff и pytest.
4. Если менялся frontend — запустить lint и build.
5. Если менялась схема базы — применить миграции отдельно.
6. Для поведения реальной модели провести ручную проверку на выбранном провайдере.
7. Сравнить результат с baseline и проверить, что сообщения, броски и источники не
   потерялись и не были придуманы моделью.

Не включайте реальные секреты в тестовые файлы. Для автоматических тестов используются
поддельные провайдеры, поэтому настоящий ключ модели обычно не нужен.

Команды проекта для локальной проверки берутся из `AGENTS.md`. Для backend применяются
Ruff и pytest; для frontend — ESLint-команда проекта и сборка; если менялась схема,
нужно отдельно применить Alembic. Успешная сборка означает, что код удалось собрать,
но не доказывает качество ответа модели или корректность содержания игры.

# Часть 11. Что именно не подтверждается этим учебником

Архитектурное описание и исходники позволяют понять устройство программы, но не
подтверждают следующие свойства конкретного компьютера или установки:

- что именно записано в локальном `backend/.env`;
- что база сейчас запущена и в ней есть нужная миграция;
- что корпус SRD импортирован и даёт хороший поиск;
- что Ollama и выбранная модель установлены и отвечают;
- что браузер и интерфейс проверены на конкретном устройстве;
- что все ответы модели литературно качественные;
- что счёт облачного провайдера равен нулю;
- что политика контента безошибочна;
- что приложение готово для публичной эксплуатации без дополнительной настройки;
- что CI workflow запустится в конкретном аккаунте GitHub.

Тесты создают таблицы из моделей приложения, поэтому успешные pytest не заменяют
проверку миграций командой Alembic. Для тестов нужна отдельная база `dnd_test`, не
обычная база пользовательских данных.

# Итог в нескольких предложениях

Игрок работает в React-интерфейсе. FastAPI-сервер проверяет аккаунт и права, хранит
данные в PostgreSQL, сам решает игровую механику, находит отрывки правил через pgvector
и отправляет отобранный контекст языковой модели. Модель пишет текст, но не владеет
кубиком, базой и правилами игры. Повторы запросов защищены от дублирования, а ошибки
модели не должны стирать уже сохранённое сообщение игрока.

У персонажа есть редактируемый лист: четыре способа получения характеристик, бонус
предыстории, правка уровня и текущих хитов, тёмное зрение и спасброски в карточке —
при этом все производные значения по-прежнему считает сервер.

Сейчас у кампании есть вступительная сцена, простое серверное распознавание поиска,
best-effort политика контента и фоновая память. При этом нет полноценного боевого
движка, подробного структурированного мира, общей модерации-модели, совместных кампаний
и общего между несколькими процессами счётчика запросов. Справочник SRD нужно импортировать
отдельно. Это рабочий MVP — минимальная полезная версия — а не полная компьютерная
симуляция D&D. **MVP** (Minimum Viable Product) — минимально полезная версия продукта:
она уже решает основную задачу, но ещё не включает все возможные функции.
