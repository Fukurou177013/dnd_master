## 1.1. Кто участвует в работе системы

Сеть работает через **порты** — числа, по которым компьютер отличает один сервис от другого. Например, два сервера на одной машине могут работать одновременно, если слушают разные порты.

| Участник | Что это физически | Адрес в проекте |
|---|---|---|
| Браузер | Программа, в которой открыт интерфейс | `http://localhost:5173` |
| Vite dev-server | Сервер, который отдаёт файлы React и пересылает запросы `/api` на backend | `http://localhost:5173` |
| Backend | Python-программа на FastAPI: правила, доступ к базе, вызовы модели | `http://localhost:8000` |
| PostgreSQL | База данных: пользователи, персонажи, кампании, сообщения, фрагменты правил | `localhost:5433` снаружи Docker |
| pgvector | Расширение PostgreSQL для хранения векторов и поиска по ним | Внутри той же базы |
| LLM-провайдер (языковая модель) | Внешний HTTP-сервис, который генерирует текст | Локально Ollama на `http://localhost:11434/v1` или другой OpenAI-совместимый адрес |
| Docker | Программа, запускающая PostgreSQL в контейнере | Только база данных |
| Ollama | Локальный сервер моделей | `http://localhost:11434` |

Важное уточнение: **Docker в этом проекте запускает только базу данных**. Backend и frontend запускаются отдельными командами. Это частая точка путаницы: если контейнер базы работает, это ещё не значит, что сайт открыт.

## 1.4. Путь одного сообщения

Разберём главный сценарий: пользователь отправляет действие в чат.

1. **Браузер.** Компонент `frontend/src/CampaignChatPage.tsx` собирает JSON:

   ```json
   {
     "content": "Я осматриваю комнату.",
     "client_message_id": "0f5c1d9e-6a15-4c5c-8c8e-2d4e4f4a9e11",
     "check": {
       "ability": "wisdom",
       "skill": "Perception",
       "dc": 15
     }
   }
   ```

   Поле `check` необязательное. Если пользователь не включил проверку в интерфейсе, сервер не будет бросать кубик.

2. **Vite-прокси.** Запрос уходит на `http://localhost:5173/api/v1/campaigns/<id>/messages`, а Vite пересылает его на `http://localhost:8000`. Для браузера это один и тот же адрес сайта, поэтому cookie сессии отправляется автоматически. В `frontend/vite.config.ts` указано `changeOrigin: false`: backend проверяет заголовок `Origin`, и подмена имени хоста привела бы к отказу изменяющих запросов.

3. **FastAPI.** Запрос проходит через:

   - middleware `reject_foreign_origins` в `app/main.py` (middleware — промежуточный слой, который обрабатывает запрос до маршрута): для методов, которые меняют данные (`POST`, `PUT`, `PATCH`, `DELETE`), чужой `Origin` получает `403`;
   - роутер `/api/v1/campaigns`;
   - зависимость `get_current_user`: читает cookie `session_token`, считает SHA-256 и ищет сессию в базе;
   - зависимость `get_db`: открывает сессию SQLAlchemy;
   - Pydantic-схему `CampaignMessageCreate`: проверяет длину текста, формат `client_message_id`, допустимые характеристики и DC.

4. **Маршрут `send_campaign_message`.** Он:

   - проверяет, что кампания принадлежит текущему пользователю, иначе возвращает `404`;
   - проверяет лимит сообщений: по умолчанию 30 в минуту на пользователя;
   - находит персонажа кампании;
   - вызывает `run_turn(...)` из `app/services/game_master.py`.

5. **Один ход мастера.** Функция `run_turn`:

   - ставит блокировку на кампанию, чтобы два одновременных запроса не создали дубликаты;
   - сохраняет сообщение пользователя или находит уже сохранённое по `client_message_id`;
   - если передана проверка, сервер сам бросает d20 и сохраняет результат;
   - делает embedding (числовой вектор смысла текста) для сообщения пользователя;
   - ищет ближайшие по смыслу фрагменты SRD в PostgreSQL через pgvector (по умолчанию 4);
   - собирает prompt (текст запроса к модели): системная инструкция, резюме кампании, результат проверки, найденные фрагменты и последние 12 сообщений;
   - отправляет prompt в LLM и получает текст;
   - сохраняет ответ мастера вместе с броском и списком источников;
   - ставит фоновую задачу на обновление резюме кампании.

6. **Ответ.** Backend возвращает JSON `CampaignExchange`:

   ```json
   {
     "user_message": { "role": "user", "content": "Я осматриваю комнату." },
     "assistant_message": {
       "role": "assistant",
       "content": "Текст мастера",
       "roll": { "d20": 14, "total": 16, "dc": 15, "success": true },
       "sources": []
     },
     "memory_update_scheduled": true
   }
   ```

   Пример сокращён: в реальном ответе есть `id`, `sequence`, `created_at` и другие поля.

7. **Браузер.** React добавляет оба сообщения в ленту, перезапрашивает кампанию, чтобы обновить блок «Память кампании», и показывает карточку броска и раскрывающийся список источников SRD.

## 1.5. Слои внутри backend

| Слой | Файлы | Зачем нужен |
|---|---|---|
| Маршруты | `app/api/v1/*` | Принимают HTTP-запрос, проверяют права, вызывают сервис, переводят исключения в коды ответа |
| Схемы | `app/schemas/*` | Pydantic-описание того, что разрешено прислать и что вернуть |
| Сервисы | `app/services/*` | Логика без знания про HTTP: броски, поиск, prompt, работа с базой |
| Модели | `app/models/*` | Таблицы базы и связи между ними через SQLAlchemy ORM |
| Правила | `app/rules/*` | Справочники D&D и вычисления, зашитые в код |
| Ядро | `app/core/*` | Настройки, пароли, токены, event loop |
| База | `app/db/*` | Движок подключения и базовый класс моделей |

SQL — язык запросов к реляционной базе данных; SQLAlchemy формирует такие запросы из операций с Python-объектами.

Такое разделение даёт три практических результата:

- логику можно тестировать без HTTP;
- LLM и кубик можно подменить в тестах;
- схему базы можно менять миграциями, не переписывая маршруты.

## 1.6. Аутентификация: как сервер понимает, что это вы

1. При регистрации пароль превращается в **Argon2-хеш** (`app/core/security.py`). Хеш — это необратимое преобразование строки; сам пароль в базе не хранится. Библиотека `argon2-cffi` по умолчанию использует вариант Argon2id.
2. При входе сервер проверяет пароль по хешу и создаёт случайный токен через `secrets.token_urlsafe(32)`.
3. В браузер уходит **httpOnly cookie** с именем `session_token`. Атрибут `httpOnly` запрещает JavaScript читать cookie, поэтому украсть токен через внедрённый скрипт сложнее.
4. В базе лежит не сам токен, а его SHA-256 в таблице `sessions`. SHA-256 — это хеш-функция: по ней нельзя восстановить исходный токен.
5. На каждом запросе `get_current_user` хеширует cookie, ищет сессию, проверяет срок действия и активность пользователя.
6. Выход удаляет сессию из базы и стирает cookie.

Дополнительные флаги cookie задаются настройками:

- `COOKIE_SECURE=true` разрешает передачу cookie только по HTTPS;
- `SESSION_COOKIE_SAMESITE` управляет отправкой cookie при переходах между сайтами;
- комбинация `SameSite=none` без `Secure` отклоняется при старте, потому что браузеры такую cookie не сохраняют.

Для запросов, которые меняют данные, сервер проверяет `Origin` — адрес сайта, с которого пришёл запрос. Если `Origin` не совпадает с текущим хостом и не входит в `CORS_ORIGINS`, возвращается `403`. Это защита от CSRF — ситуации, когда чужой сайт пытается отправить запрос от имени пользователя.

Чужие персонажи и кампании возвращают `404`, а не `403`, чтобы не раскрывать сам факт их существования.

## 1.7. Таблицы базы данных

| Таблица | Что хранит | Важные ограничения |
|---|---|---|
| `users` | email, хеш пароля, имя, активность | email уникален и хранится в нижнем регистре |

| `campaign_memories` | структурированное резюме кампании в JSONB (двоичный JSON-тип PostgreSQL) | одна запись на кампанию |
| `campaign_messages` | роль, текст, порядковый номер, `client_message_id`, JSON с броском и источниками | уникальность `(campaign_id, sequence)` и `(campaign_id, client_message_id)` |
| `srd_chunks` | фрагмент правил, раздел, заголовок, текст, вектор, лицензия | уникальный `chunk_key`; вектор `vector(1024)`; HNSW-индекс |
| `alembic_version` | текущая версия схемы | служебная таблица миграций |

В таблице персонажей HP — хиты (запас здоровья), AC — класс брони (число, которое должна достичь атака, чтобы попасть).

Поле `sequence` — порядковый номер сообщения внутри кампании. Ограничение `UNIQUE (campaign_id, sequence)` не даёт двум сообщениям получить один номер. Ответ мастера хранит в JSON `reply_to` — идентификатор сообщения пользователя, на которое он отвечает.

В `campaign_memories.summary` лежит JSON с пятью массивами строк:

```json
{
  "facts": ["установленные факты"],
  "goals": ["цели персонажа и группы"],
  "npcs": ["важные NPC"],
  "locations": ["важные локации"],
  "open_threads": ["незавершённые события и вопросы"]
}
```

Это резюме, а не полное состояние мира. В нём нет текущей сцены, позиции персонажа, видимых предметов и очерёдности ходов.

Текущая голова миграций по README — `5d9b1e4a7c20` (миграция на `vector(1024)`). На момент аудита файл этой миграции был в рабочем дереве, но ещё не отслеживался Git. Перед запуском стоит проверить `git status` и `uv run alembic current`.

## 1.8. Коды ответов, которые важно различать

| Код | Когда возвращается | Что означает для пользователя |
|---|---|---|
| `200` | Успешный запрос | Данные получены |
| `201` | Создание пользователя, персонажа или кампании | Объект создан |
| `204` | Удаление или выход | Тело ответа пустое |
| `401` | Нет cookie или сессия истекла | Нужно войти заново |
| `403` | Чужой `Origin` | Запрос отклонён защитой от CSRF |
| `404` | Кампания или персонаж не найдены либо принадлежат другому | Чужие данные не раскрываются |
| `409` | Email уже зарегистрирован | Нужен другой email |
| `422` | Неверные поля: характеристика, навык, DC, текст | Запрос не прошёл проверку |
| `429` | Превышен лимит сообщений | Нужно подождать |
| `503` | LLM-провайдер недоступен или не настроен | Сообщение пользователя уже сохранено; можно повторить |
| `504` | LLM-провайдер не ответил вовремя | То же |

## 2.3. Инфраструктура

**Docker Compose** описан в `backend/docker-compose.yml`. Он запускает один сервис `db`:

- образ `pgvector/pgvector:pg17` — PostgreSQL 17 с уже установленным расширением `vector`;
- пользователь, пароль и база — `dnd/dnd/dnd`;
- порт хоста `5433` связан с портом контейнера `5432`;
- данные лежат в volume `pgdata`, поэтому не пропадают при перезапуске контейнера;
- healthcheck проверяет готовность базы командой `pg_isready`.

Порт `5433` выбран специально, чтобы не конфликтовать с PostgreSQL, который может быть установлен на компьютере и слушать стандартный `5432`.

**Ollama** — локальный сервер моделей. Проект обращается к нему по OpenAI-совместимому адресу `http://localhost:11434/v1`: это значит, что формат запросов такой же, как у OpenAI, но запросы идут на ваш компьютер. В README описаны две модели:

- `qwen3:14b` — отвечает в чате;
- `qwen3-embedding-cpu` — строит embeddings; вариант собран с `PARAMETER num_gpu 0`, чтобы не занимать видеопамять рядом с чат-моделью.

**Windows и event loop.** Event loop — цикл обработки событий, который управляет асинхронными операциями. На Windows backend запускают с флагом `--loop app.core.loop:selector_loop_factory`. Причина: драйвер `psycopg` не работает с `ProactorEventLoop`, который uvicorn использует на Windows по умолчанию. Без этого флага база может не подключиться. Скрипт импорта SRD тоже выбирает `SelectorEventLoop` на Windows.

**`start.bat`** автоматизирует запуск:

1. проверяет наличие Docker, `uv` и `npm.cmd`;
2. запускает контейнер базы;
3. если нет `backend/.env`, копирует `.env.example` и подставляет `dnd:dnd@localhost:5433/dnd`;
4. устанавливает зависимости, если их нет;
5. применяет миграции;
6. запускает backend и frontend, затем открывает браузер;
7. команда `start.bat stop` останавливает процессы и контейнер базы.

Импорт SRD в `start.bat` не входит. Поэтому после первого запуска чат работает, но источники SRD могут быть пустыми, пока корпус не импортирован вручную.

## 2.5. Переменные окружения

Настройки читаются в `app/core/config.py`. Значения по умолчанию в коде и значения из `.env.example` — это разные вещи. OpenAI — облачный провайдер языковых моделей; локальная Ollama отвечает на запросы в совместимом формате. Таблица ниже показывает оба случая.

| Переменная | Значение в коде | Что означает |
|---|---|---|
| `DATABASE_URL` | нет значения; обязательна | Адрес базы для SQLAlchemy, например `postgresql+psycopg://dnd:dnd@localhost:5433/dnd` |
| `COOKIE_SECURE` | `false` | `true` только для HTTPS |
| `SESSION_TTL_DAYS` | `30` | Срок жизни cookie-сессии в днях |
| `SESSION_COOKIE_SAMESITE` | `lax` | `lax`, `strict` или `none`; `none` требует `COOKIE_SECURE=true` |
| `CORS_ORIGINS` | пустая строка | Список разрешённых origin через запятую, если фронтенд не через прокси |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | База OpenAI-совместимого API |
| `LLM_API_KEY` | пустая строка | Ключ провайдера; хранится только на backend |
| `LLM_CHAT_MODEL` | `gpt-4o-mini` | Модель чата |
| `LLM_EMBEDDING_MODEL` | `text-embedding-3-small` | Модель embeddings |
| `LLM_EMBEDDING_DIMENSIONS` | `1024` | Размерность вектора; должна совпадать с `vector(1024)` |
| `LLM_TIMEOUT_SECONDS` | `30.0` | Тайм-аут запросов к провайдеру |
| `LLM_MAX_OUTPUT_TOKENS` | `700` | Ограничение длины ответа модели |
| `LLM_TEMPERATURE` | `0.7` | Степень вариативности ответа |
| `LLM_SYSTEM_SUFFIX` | пустая строка | Текст, который добавляется к системной инструкции; для Qwen3 в примере указан `/no_think` |

| `RECENT_MESSAGE_LIMIT` | `12` | Сколько последних сообщений входит в prompt |

Важно: **значение по умолчанию в коде не доказывает, что приложение сейчас обращается к OpenAI**. Фактическое значение задаётся файлом `backend/.env`, который в рамках этого аудита не открывался. README и `.env.example` описывают локальную конфигурацию Ollama. Если файла `.env` нет, `start.bat` создаст его из примера; если файл есть, но в нём остался адрес OpenAI и присутствует ключ, запросы могут уйти в платный сервис. Если ключ пуст, провайдер вернёт `503` и HTTP-запрос к внешнему сервису не отправится.

# Часть 3. Словарь новичка

Ниже 15 терминов, без которых нельзя прочитать остальные части. Остальные термины объясняются по месту.

### 1. API

API (Application Programming Interface, программный интерфейс) — набор адресов и правил, по которым одна программа обращается к другой. В проекте API — это маршруты вида `/api/v1/campaigns`, `/api/v1/characters`. Браузер не работает с базой напрямую: он отправляет HTTP-запрос на API, а backend уже решает, что прочитать или записать.

### 2. HTTP

HTTP — протокол передачи запросов и ответов в вебе. У запроса есть метод (`GET` — прочитать, `POST` — создать или отправить, `PATCH` — изменить, `DELETE` — удалить), адрес и тело. У ответа есть код состояния: `200` — успех, `404` — не найдено, `503` — сервис недоступен. В проекте HTTP используется между браузером и Vite, между Vite и FastAPI, а также между backend и LLM-провайдером.

### 3. JSON

JSON — текстовый формат данных с парами «ключ — значение». Пример из проекта:

```json
{
  "content": "Я осматриваю комнату.",
  "check": { "ability": "wisdom", "skill": "Perception", "dc": 15 }
}
```

Backend принимает JSON, проверяет его Pydantic-схемой и возвращает JSON. JSON удобен тем, что его понимают и Python, и JavaScript.

### 4. Cookie, httpOnly, SameSite

Cookie — небольшая строка, которую сервер просит браузер сохранить и автоматически прикладывать к последующим запросам на тот же сайт. В проекте cookie `session_token` заменяет повторный ввод пароля.

- `httpOnly` запрещает JavaScript читать cookie; это снижает риск кражи токена.
- `SameSite` управляет тем, будет ли cookie отправлена при переходе с другого сайта. `lax` — безопасный компромисс для обычного веб-приложения.
- `Secure` разрешает отправку только по HTTPS.

Сервер хранит не саму cookie, а её SHA-256 в таблице `sessions`.

### 5. Origin, same-origin, CORS

**Origin** — комбинация схемы, хоста и порта, например `http://localhost:5173`. Два адреса считаются **same-origin**, если у них совпадают все три части.

**CORS** (Cross-Origin Resource Sharing) — правила, по которым сервер разрешает или запрещает запросы с другого origin. В проекте фронтенд и backend выглядят для браузера как один origin благодаря прокси Vite. Если фронтенд открыт отдельно, backend требует явно перечислить его origin в `CORS_ORIGINS`; wildcard `*` запрещён, потому что API использует cookie.

### 6. ORM

ORM (Object-Relational Mapping) — способ работать с таблицами базы как с обычными классами Python. В `app/models/campaign.py` класс `CampaignMessage` соответствует таблице `campaign_messages`, а его поля — колонкам. SQLAlchemy переводит операции с объектами в SQL-запросы. Это уменьшает количество ручного SQL, но не отменяет необходимости понимать, какие запросы выполняются.

### 7. Миграция

Миграция — версионированное изменение схемы базы. Файл миграции описывает, как перейти от одной версии таблиц к другой. Alembic хранит применённые версии в таблице `alembic_version`. Если изменить модель, но не создать миграцию, база и код разойдутся. В проекте миграции лежат в `backend/alembic/versions/`.

### 8. Docker, образ, контейнер, volume

Docker — программа, которая запускает приложение в изолированной среде.

- **Образ** — шаблон с программой и её зависимостями, например `pgvector/pgvector:pg17`.
- **Контейнер** — запущенный экземпляр образа.
- **Volume** — постоянное хранилище данных, которое не удаляется вместе с контейнером.

В проекте Docker нужен только для PostgreSQL. Если удалить volume, данные базы пропадут, даже если код остался.

### 9. LLM

LLM (Large Language Model, большая языковая модель) — модель, которая генерирует текст по входному описанию. В проекте LLM не встроена в код: backend отправляет HTTP-запрос на OpenAI-совместимый адрес и получает текст. Локально это Ollama, удалённо — другой провайдер. Модель не хранит состояние кампании: каждый запрос содержит нужный контекст заново.

### 10. Prompt

Prompt (запрос к модели) — текст, который отправляется модели. В проекте prompt состоит из системной инструкции, резюме кампании, результата проверки, найденных фрагментов SRD и последних сообщений. Системная инструкция задаёт роль, язык, длину ответа и запрет придумывать броски. Модель видит только то, что попало в prompt.

### 11. Embedding и вектор

Embedding — числовой вектор, который представляет смысл текста. Похожие по смыслу тексты дают близкие векторы. В проекте embedding строит отдельная модель, а не чат-модель. Вектор запроса сравнивается с векторами фрагментов SRD; чем меньше косинусное расстояние, тем ближе смысл.

### 12. RAG

RAG (Retrieval-Augmented Generation, генерация с поиском) — подход, при котором перед ответом модели находят релевантные документы и вставляют их в prompt. В проекте RAG ищет фрагменты SRD по смыслу и передаёт их мастеру. Это не гарантирует правильность ответа: модель может неверно понять найденный текст, а поиск может не найти нужный раздел.

### 13. pgvector и косинусное расстояние

pgvector — расширение PostgreSQL, которое хранит векторы в колонке типа `vector(1024)` и умеет искать ближайшие. **Косинусное расстояние** измеряет угол между векторами: чем меньше значение, тем больше сходство направлений. **Индекс** — вспомогательная структура базы, которая ускоряет поиск. В проекте используется индекс HNSW с оператором `vector_cosine_ops`; HNSW — структура индекса для быстрого приблизительного поиска ближайших векторов.

### 14. SRD

SRD (System Reference Document) — открытая часть правил D&D 5e. В проекте используется SRD 5.2.1 под лицензией CC BY 4.0. Корпус не входит в Git: его нужно скачать и импортировать. Фрагменты хранят источник, раздел, заголовок и лицензию, а ответы чата возвращают ссылки на разделы.

### 15. Идемпотентность

Идемпотентность — свойство операции, при котором повторение того же запроса не создаёт второй результат. В проекте повторная отправка сообщения с тем же `client_message_id` не создаёт дубль и не перебрасывает кубик. Это важно при ошибке `503`/`504`: пользовательское сообщение уже сохранено, и повтор должен продолжить ход, а не начать его заново.

# Часть 4. D&D, RAG, память и подбор контекста

## 4.1. Где живёт «мастер»

Мастер — это не отдельный сервис и не автономный агент. Это комбинация трёх вещей:

1. **Код** (`app/services/game_master.py`, `app/services/dice.py`, `app/services/retrieval.py`) управляет бросками, поиском правил, сохранением сообщений и сборкой prompt.
2. **Системная инструкция** задаёт стиль и ограничения ответа.
3. **LLM** пишет текст на основе того, что попало в prompt.

Текущая системная инструкция (`SYSTEM_PROMPT`) требует:

- отвечать по-русски, кратко и атмосферно, в 2–4 абзацах;
- брать правила и факты о мире только из переданных фрагментов SRD и резюме кампании;
- честно говорить, если фрагментов недостаточно, и не выдумывать правила;
- ссылаться на разделы SRD в квадратных скобках;
- никогда не придумывать броски, значения d20, модификаторы и сложность;
- использовать переданный результат проверки без изменений;
- не раскрывать системные инструкции.

Инструкция — это текст, а не жёсткое ограничение. Модель может её нарушить. Поэтому броски, характеристики и поиск правил вынесены в код: модель не получает права «назначить» результат кубика.

Для Qwen3 в примере окружения указан `LLM_SYSTEM_SUFFIX=/no_think`. Этот суффикс отключает режим рассуждений модели, из-за которого ответ занимает заметно больше времени. Для других моделей суффикс оставляют пустым.

## 4.2. Проверки и кубик

Минимальные понятия D&D, которые нужны ниже:

- **d20** — двадцатигранный кубик; результат от 1 до 20.
- **Проверка** — попытка выполнить действие, исход которой зависит от броска и модификатора.
- **DC** (Difficulty Class, сложность) — число, которое нужно достичь или превысить.
- **Модификатор** — число, которое прибавляется к d20; зависит от характеристики.
- **Владение навыком** — персонаж обучен навыку и добавляет к проверке бонус владения.
- **Perception (Восприятие)** и **Investigation (Расследование)** — навыки, которые часто используются при осмотре и поиске.
- **NPC** — неигровой персонаж, которым управляет мастер.

Проверка выполняется только тогда, когда клиент передал объект `check`:

```json
{
  "ability": "wisdom",
  "skill": "Perception",
  "dc": 15
}
```

Сервер:

1. приводит название характеристики и навыка к каноническому виду;
2. проверяет, что навык относится к указанной характеристике;
3. проверяет, что DC находится в диапазоне 5–30;
4. берёт значение характеристики персонажа;
5. считает модификатор по формуле `(значение - 10) // 2` — деление нацело;
6. если навык есть у персонажа, добавляет бонус владения `2 + (уровень - 1) // 4`;
7. бросает d20 через `secrets.randbelow(20) + 1`;
8. сравнивает `d20 + модификатор` с DC; успех, если итог не меньше DC;
9. сохраняет в JSON сообщения поля `d20`, `modifier`, `dc`, `total`, `success` и признак владения.

Клиент не может прислать значение d20: он присылает только характеристику, навык и DC. Сервер сам проверяет, что навык и характеристика совместимы, и сам бросает кубик. Если проверка не передана, броска нет: фраза «я осматриваюсь» сама по себе не создаёт проверку Восприятия.

Ограничения текущей механики:

- нет преимущества и помехи;
- нет критических успехов и провалов;
- нет автоматического выбора проверки по тексту действия;
- нет брони, оружия и боевых действий;
- DC выбирает клиент, а не сервер по правилам;
- результат проверки передаётся модели, но лист персонажа в prompt не попадает. Имя, класс, HP и остальные поля не передаются отдельным блоком; они могут встретиться только в тексте истории или резюме. Число модификатора модель видит в описании проверки.

## 4.3. Импорт SRD: офлайн-подготовка

Корпус SRD не хранится в репозитории. Его нужно положить в `backend/data/srd/` и импортировать командой `uv run python -m app.scripts.import_srd ...`.

Поддерживаются два формата:

- Markdown или текст с заголовками от `#` до `######`; разделы режутся по заголовкам;
- JSONL (формат, где каждая строка — отдельный JSON-объект) с полями `section`, `title`, `content` и необязательными `source`, `license`, `metadata`.

Правила нарезки в `app/scripts/import_srd.py`:

- максимальный размер фрагмента — 1600 символов;
- слишком короткие фрагменты (меньше 200 символов) могут присоединяться к предыдущему фрагменту того же раздела;
- длинный абзац режется на части по 1600 символов;
- для Markdown сохраняется путь заголовков, например `Using Ability Scores / Ability Checks`.

Ключ фрагмента — SHA-256 от строки `источник|раздел|текст`. Повторный импорт пропускает уже существующие фрагменты. Это делает импорт идемпотентным: запуск второй раз не создаёт копии.

Embedding строится не только по тексту, но и по разделу и заголовку:

```text
{section}
{title}

{content}
```

Векторы отправляются пачками по 32 фрагмента. Каждый фрагмент хранит `source`, `section`, `title` и `license`; `source_url`, имя файла и путь заголовков лежат в JSON-метаданных. В ответ чата возвращаются `source`, `section`, `title`, `license` и excerpt; `source_url` и полный текст фрагмента в ответ не попадают.

Размерность вектора жёстко связана со схемой:

- в `app/core/config.py` задано `EMBEDDING_DIMENSIONS = 1024`;
- колонка `srd_chunks.embedding` имеет тип `vector(1024)`;
- при старте приложение проверяет, что `LLM_EMBEDDING_DIMENSIONS` совпадает с 1024;
- при смене модели нужно изменить константу, создать миграцию и заново импортировать корпус.

Миграция `5d9b1e4a7c20` переводит колонку на 1024 измерения. Её `downgrade` очищает таблицу `srd_chunks`, потому что векторы другой размерности нельзя корректно преобразовать обратно.

## 4.4. Онлайн-поиск: что происходит на каждом ходу

1. Backend берёт текст сообщения пользователя как поисковый запрос.
2. Отправляет его embedding-модели и получает один вектор.
3. Считает косинусное расстояние между этим вектором и векторами всех фрагментов SRD.
4. Сортирует по расстоянию и берёт `RETRIEVAL_TOP_K` фрагментов, по умолчанию 4.
5. Возвращает фрагменты в prompt и в ответ API.

Важные особенности:

- порога сходства нет: даже далёкий фрагмент может попасть в топ-4;
- переранжирования и ключевого поиска нет;
- запрос не переписывается и не дополняется синонимами;
- если корпус не импортирован, список фрагментов пуст, и модель получает строку «Фрагменты SRD не найдены. Не выдумывай правила»;
- если embedding-провайдер недоступен, `run_turn` перехватывает `ProviderError`, пишет предупреждение в лог и продолжает без источников;
- ошибки базы данных этим перехватом не покрываются и могут привести к `500`.

В prompt текст фрагмента обрезается до 1800 символов. В ответе API (`sources`) хранится excerpt до 400 символов, а также `id`, `source`, `section`, `title`, `license`. Полный текст фрагмента в ответе чата не отдаётся.

## 4.5. Память кампании: два слоя

Память состоит из двух разных механизмов.

**Слой 1. История сообщений.** Все сообщения лежат в `campaign_messages` с порядковым номером. В prompt попадают только последние `RECENT_MESSAGE_LIMIT` сообщений, по умолчанию 12. История в интерфейсе запрашивается отдельно: `GET /api/v1/campaigns/{id}/messages` по умолчанию отдаёт 100 сообщений, максимум 500.

**Слой 2. Структурированное резюме.** В `campaign_memories.summary` хранится JSON с пятью массивами: факты, цели, NPC, локации, незавершённые события. Резюме обновляется после успешного хода отдельным вызовом модели.

Как обновляется резюме:

1. После ответа мастера создаётся фоновая задача `_update_campaign_summary`.
2. Она открывает отдельную сессию базы.
3. Берёт текущее резюме и последние 12 сообщений.
4. Отправляет модели `SUMMARY_PROMPT` с требованием вернуть только JSON (temperature 0.2, max_tokens 1500).
5. Разбирает JSON, проверяет его схемой `CampaignSummary` и сохраняет.
6. Если провайдер недоступен, пишет предупреждение и оставляет старое резюме.
7. Если JSON повреждён, также оставляет старое резюме.

Что важно понимать:

- резюме обновляется не в той же транзакции, что сообщения; фоновой задаче может не хватить времени, если процесс завершится сразу после ответа;
- `memory_update_scheduled: true` в ответе означает «задача поставлена», а не «резюме уже обновлено»;
- резюме не является полным состоянием мира: в нём нет текущей сцены, позиции персонажа, видимых объектов и очерёдности;
- резюме — это текст, сгенерированный моделью, а не проверенные правила;
- ошибка обновления резюме не удаляет сообщения и не ломает ответ.

В интерфейсе резюме показано в боковой панели «Память кампании». Пустые разделы отображаются как «Пока пусто».

## 4.6. Как собирается prompt

Порядок в `app/services/game_master.py`:

```text
system:
  SYSTEM_PROMPT
  Резюме кампании:
    Факты: ...
    Цели: ...
    NPC: ...
    Локации: ...
    Незавершённые события: ...
  Результат проверки:
    Проверка Мудрость (Perception): d20=14, модификатор=+2, итог=16,
    сложность=15, успех. Используй этот результат без изменений.
  Фрагменты SRD:
    [1] Название (раздел)
    Источник: ... Лицензия: ...
    текст фрагмента

user/assistant:
  последние 12 сообщений истории
```

Если проверки не было, вместо результата стоит строка «Проверка не выполнялась». Если фрагментов нет — строка «Фрагменты SRD не найдены. Не выдумывай правила».

В системную инструкцию также добавляется `LLM_SYSTEM_SUFFIX`, если он задан. Ответ модели ограничен `LLM_MAX_OUTPUT_TOKENS` (по умолчанию 700) и температурой `LLM_TEMPERATURE` (по умолчанию 0.7).

Чего в prompt нет:

- листа персонажа (кроме числа модификатора в проверке);
- текущей сцены и состояния мира;
- результата классификации намерения;
- правил политики контента;
- возраста пользователя;
- инструкций по безопасности.

Именно поэтому фраза «я осматриваюсь» не получает особой обработки: для кода это обычный текст, а для модели — часть истории. Если в резюме или предыдущих сообщениях нет описания комнаты, модель может придумать детали или отказаться от описания. Системная инструкция запрещает выдумывать правила, но не даёт готового описания сцены.

## 4.8. Надёжность: почему повтор не ломает игру

**Идемпотентность.** У сообщения пользователя есть `client_message_id`. Пара `(campaign_id, client_message_id)` уникальна. Если тот же запрос придёт повторно:

- при наличии ответа мастера сервер вернёт сохранённую пару сообщений;
- если ответа нет, сервер возьмёт сохранённый результат броска из JSON сообщения и продолжит с того же места;
- новый бросок не выполняется.

**Блокировка кампании.** `_lock_campaign` вызывает `pg_advisory_xact_lock` с хешем идентификатора кампании. Это блокировка на время транзакции (транзакция — набор операций с базой, которые применяются вместе): два одновременных запроса к одной кампании выполняются по очереди. Без неё возможны дубликаты и конфликт порядковых номеров.

**Нумерация.** `next_sequence` берёт максимальный номер и добавляет единицу. Ограничение уникальности `(campaign_id, sequence)` защищает от сбоя порядка.

**Ошибки провайдера.** Если модель недоступна или не ответила вовремя:

- пользователь получает `503` или `504`;
- сообщение пользователя уже сохранено;
- повтор с тем же `client_message_id` не дублирует его;
- ответ мастера появится после успешного повторного вызова.

**Лимит запросов.** `allow_request` хранит временные метки в памяти процесса. По умолчанию разрешено 30 сообщений в минуту на пользователя. После перезапуска счётчики обнуляются. Если запустить несколько процессов, у каждого будет свой счётчик; для общего лимита нужен внешний сервис вроде Redis.

**Сбои резюме.** Ошибка фонового обновления не влияет на уже сохранённые сообщения. Старое резюме остаётся, пока не будет успешного обновления.

## 4.9. Как тесты помогают понять систему

В `backend/tests/conftest.py` подменяются три зависимости:

```python
app.dependency_overrides[get_chat_provider] = lambda: fake_chat
app.dependency_overrides[get_embedding_provider] = lambda: fake_embeddings
app.dependency_overrides[get_roll_generator] = lambda: roll_generator
```

- `FakeChatProvider` возвращает заранее заданный ответ мастера и JSON резюме;
- `FakeEmbeddingProvider` возвращает одинаковый детерминированный вектор;
- `FixedRollGenerator` всегда выдаёт заданное значение d20, по умолчанию 20.

Тестовая база `dnd_test` создаётся автоматически. Схема создаётся не через Alembic, а через `Base.metadata.create_all`, а между тестами таблицы очищаются. Поэтому тесты проверяют код, но не проверяют, что миграции соответствуют моделям.

Что покрыто тестами:

- изоляция аккаунтов;
- запрет чужого персонажа и чужой кампании;
- детерминированный бросок;
- источники SRD;
- идемпотентность по `client_message_id`;
- повтор после ошибки провайдера;
- сохранение сообщения при `503` и `504`;
- несовпадение навыка и характеристики;
- ответ без retrieval и без проверки;
- ошибка и повреждённый JSON резюме;
- отсутствие дубля ответа мастера.

Чего тесты не покрывают:

- реальное качество ответов Ollama;
- политику контента;
- вступительную сцену;
- классификацию намерений;
- работу лимита при нескольких процессах;
- соответствие миграций моделям;
- поведение браузера и доступность интерфейса.

- Личные кампании, журнал сообщений и отдельное структурированное резюме.
- Поиск по SRD через PostgreSQL и pgvector, ответы со ссылками на разделы.
- Проверки характеристик и навыков: сервер бросает d20, применяет модификатор и сохраняет d20, модификатор, DC, итог и успех.
- Повтор с тем же `client_message_id` не дублирует сообщения и не перебрасывает кубик.
- Ошибки чат-провайдера возвращаются как `503`/`504`, сообщение пользователя сохраняется; сбой embedding-провайдера при поиске SRD не блокирует ответ (ошибки самой базы не перехватываются).
- Фоновое обновление резюме; ошибка обновления не удаляет историю.
- Тесты не требуют реального ключа LLM.
- `start.bat` поднимает базу, применяет миграции, запускает backend и frontend.

## 5.2. Чего пока нет

| Область | Состояние | Следствие |
|---|---|---|
| Вступление кампании | При создании кампании создаётся только запись кампании и пустое резюме; сообщений нет | Чат показывает «Мастер ждёт вашего действия»; игрок начинает без сцены |

| Автоматические проверки | Нет | Проверка выполняется только если клиент её прислал |
| Преимущество и помеха | Нет | Механика d20 упрощена |
| Бой, заклинания, инвентарь | Нет | Это следующий этап, а не ошибка текущего |

| Поиск по истории | Нет | История отдаётся списком, поиска нет |
| Стриминг ответа | Нет | Пользователь ждёт весь ответ целиком |
| Учёт токенов и стоимости | Нет | Нельзя увидеть расход по кампании |
| Общий rate limiter | Нет | Лимит живёт в памяти одного процесса |

| Production-развёртывание | Нет | README прямо относит его к внешнему списку |

## 5.3. Несоответствия и рискованные места

1. **Политика Go не обеспечена кодом.** `OPENCODE_GO_POLICY.md` утверждает, что `config.py` отклоняет Go-эндпоинт. В `config.py` такой проверки нет. Это нужно либо реализовать, либо исправить документ.
2. **Политика и `AGENTS.md` не отслеживаются Git.** `.gitignore` игнорирует `AGENTS.md`, `OPENCODE_GO_POLICY.md` и старый `ARCHITECTURE_GUIDE.md`. Локально они есть, но в истории репозитория их может не быть.
3. **Default в коде — OpenAI, а не Ollama.** `LLM_BASE_URL` по умолчанию равен `https://api.openai.com/v1`, модели — `gpt-4o-mini` и `text-embedding-3-small`. Это не доказывает, что приложение сейчас использует OpenAI, потому что `.env` переопределяет значения. Но если в `.env` остался адрес OpenAI и присутствует действующий ключ, запросы могут стать платными; при пустом ключе провайдер вернёт `503` без сетевого запроса.
4. **`backend/.env` не проверялся.** В этом аудите файл не открывался. Утверждения о локальной Ollama основаны на README, `.env.example` и политике, а не на чтении секретов.
5. **Миграция `5d9b1e4a7c20` была неотслеживаемой.** На момент аудита файл существовал в рабочем дереве, но Git его не отслеживал. README ожидает эту голову. Перед запуском стоит проверить `alembic current`.
6. **SRD не импортируется автоматически.** `start.bat` не импортирует корпус. Пока корпус не импортирован, ответы будут без источников.
7. **Retrieval перехватывает только `ProviderError`.** Ошибка базы при поиске не превращается в ответ без источников.
8. **Лимит запросов не общий.** При нескольких процессах или экземплярах ограничение будет отдельным для каждого.
9. **Резюме обновляется фоном.** `memory_update_scheduled` не гарантирует, что резюме уже обновлено к моменту ответа.
10. **Старый учебник устарел в деталях.** Например, он показывает `memory_updated`, а текущее поле — `memory_update_scheduled`. Поэтому новый файл создан отдельно, а старый не перезаписывался.

# Часть 6. Git: термины, текущее состояние, минимальная стратегия

## 6.1. Терминология

Выражение «Git-архитектура» не является стандартным. Обычно различают два разных понятия:

| Понятие | Что означает | Пример в проекте |
|---|---|---|
| Структура репозитория | Расположение каталогов и файлов | Монорепозиторий с `backend/` и `frontend/` |
| Стратегия ветвления, Git workflow | Правила работы с ветками, слияниями и релизами | Стабильная `main` и короткоживущие feature-ветки |

Другие термины:

- **Репозиторий** — хранилище файлов и истории изменений.
- **Коммит** — сохранённый набор изменений с сообщением.
- **Ветка** — отдельная линия коммитов.
- **Remote** — удалённый репозиторий, например GitHub.
- **Tracking branch** — локальная ветка, связанная с удалённой; `git status` показывает, опережает она remote или отстаёт.
- **Merge** — слияние веток.
- **Worktree** — отдельная рабочая копия того же репозитория на диске, связанная с другой веткой.
- **Pull request (PR)** — предложение влить ветку в другую через интерфейс GitHub.
- **CI** — автоматический запуск проверок при коммите или PR.

## 6.2. Текущее состояние

На момент аудита:

- репозиторий один, с каталогами `backend/` и `frontend/`; это монорепозиторий (один репозиторий для нескольких частей проекта);
- текущая ветка — `feature/character-sheet`, она отслеживает `origin/feature/character-sheet`;
- есть локальные ветки `main` и `backend_dev`; `backend_dev` тоже связана с `origin/backend_dev`;
- remote — `https://github.com/Fukurou177013/dnd_master.git`;
- в `.kilo/worktrees/` есть отдельная рабочая копия (worktree) с локальной веткой `roomy-tungsten`; это инфраструктура Kilo, а не часть приложения;
- в рабочем дереве были изменены файлы `backend/.env.example`, `backend/README.md`, `backend/app/core/config.py`, `backend/app/main.py`, `backend/app/scripts/import_srd.py`, `backend/app/services/llm.py`, `backend/tests/test_campaigns.py`;
- не отслеживались миграция `backend/alembic/versions/5d9b1e4a7c20_resize_srd_embedding_to_1024.py` и файл `nul` в корне;
- CI-workflow в доступных файлах не обнаружен;
- формального стандарта сообщений коммитов в доступных файлах не обнаружено.

Эти изменения рабочего дерева — не «мусор» и не повод начинать новую сессию. Причина их появления и авторство в этой задаче не устанавливались. Их не нужно откатывать, stage-ить или удалять без отдельного решения.

## 6.3. Минимальная рекомендация

Для одиночной разработки MVP достаточно простой схемы:

1. `main` — стабильная ветка. В неё попадает только проверенный код.
2. Feature-ветка — короткая ветка под одну задачу, например `feature/opening-scene`.
3. После проверки — merge в `main`; для себя можно делать это локально, для обсуждения — через PR.
4. `backend_dev` как постоянная интеграционная ветка не обязательна. Она полезна, только если несколько человек регулярно собирают backend-изменения вместе. Если такой необходимости нет, её можно не использовать.
5. CI можно добавить позже: минимум — `ruff`, `pytest`, `npm run lint`, `npm run build`.
6. Секреты не коммитить. `.env` уже в `.gitignore`.

Что не нужно делать сейчас:

- перестраивать Git workflow ради самого workflow;
- переписывать историю;
- добавлять новый учебник в `.gitignore`;
- удалять `backend_dev`, `roomy-tungsten` или рабочую копию без отдельного решения;
- трогать незакоммиченные файлы.

# Часть 7. Приоритетный план развития

Порядок важен: сначала убрать неоднозначность инфраструктуры, затем зафиксировать поведение, и только потом расширять генерацию.

## Шаг 1. Сделать бесплатный локальный путь однозначным

**Зачем.** Сейчас в коде есть default OpenAI, а политика Go не обеспечена проверкой. Пользователь должен быть уверен, что игровой трафик не уходит в платный сервис и тем более не в Go.

**Что сделать.**

- Оставить локальную Ollama рекомендуемой конфигурацией приложения.
- Отдельно описать, что облачный провайдер — ручная опция с отдельной тарификацией.
- Добавить в `config.py` проверку: если `LLM_BASE_URL` указывает на Go-эндпоинт вида `opencode.ai/.../go`, старт отклоняется с понятным сообщением.
- Не запрещать все облачные адреса: политика запрещает Go, а не любого провайдера.
- Покрыть проверку тестами: Go-URL отклоняется, Ollama-URL принимается, обычный OpenAI-URL принимается, если он разрешён как ручная опция.
- Решить, должен ли `LLM_BASE_URL` иметь default OpenAI. Безопаснее сделать локальный адрес явным требованием `.env` или добавить отдельный режим `local`/`cloud`. Это рекомендация, а не уже принятое решение.
- Проверить, что `.env` создаётся из примера и что в примере нет секретов.

**Как проверить.**

- Юнит-тест настроек без реального ключа.
- Запуск с Go-URL должен падать на старте, а не при первом сообщении.
- Запуск с Ollama-URL должен проходить.

**Чего не делать.**

- Не подключать Go к backend.
- Не хранить ключи OpenCode в `.env.example`, коде или тестах.
- Не блокировать облачного провайдера, если пользователь сознательно выбрал его вручную.

## Шаг 2. Зафиксировать сценарии приёмки и baseline

**Зачем.** Baseline — это зафиксированный набор примеров и результатов до изменений. Пока качество мастера оценивается вручную и без такого набора, любое изменение prompt или модели нельзя сравнить с предыдущим.

**Что сделать.**

- Записать набор фраз и ситуаций:

  - «осматриваюсь», «оглядываюсь», «прислушиваюсь», «обыскиваю комнату», «что я вижу?»;
  - пустой контекст: новая кампания без истории;
  - пустой retrieval: SRD не импортирован;
  - сбой retrieval: embedding-провайдер недоступен;
  - недоступность чат-модели;
  - тайм-аут;
  - повтор с тем же `client_message_id`;
  - несовпадение навыка и характеристики;
  - слишком длинное сообщение;
  - сообщение без проверки и сообщение с проверкой.

- Для каждого случая записать ожидаемое поведение: код ответа, наличие броска, наличие источников, сохранение сообщения.
- Прогнать baseline на локальной Ollama и сохранить примеры ответов, время ответа и замеченные проблемы.
- Отдельно отметить, что качество зависит от модели, железа и квантования; README упоминает около 20 секунд для `qwen3:14b` с `/no_think`, но это не гарантия для другой машины.

**Как проверить.** Повторить тот же набор после изменений и сравнить не только текст, но и инварианты: бросок не выдуман, источники не подделаны, сообщение не потеряно.

## Шаг 3. Сделать вступление кампании

**Зачем.** Сейчас новая кампания открывается пустым чатом. Игрок не получает сцену, место, тон и повод действовать. Это первая пользовательская проблема, которую видно сразу.

**Что сделать.**

- Определить, где хранить вступление. Минимальный вариант — сохранить первое сообщение мастера в `campaign_messages` с метаданными вида `kind: "intro"`. Более полный вариант — добавить в кампанию поля сцены: место, описание, тон, предыстория.
- При создании кампании сформировать вступление: либо шаблонным текстом, либо вызовом модели с fallback (заранее подготовленным запасным вариантом на случай ошибки).
- Если модель недоступна, сохранить понятный шаблонный текст, чтобы чат не оставался пустым. Пользователь не должен видеть пустоту из-за ошибки провайдера.
- Показывать вступление как обычное сообщение мастера; убрать пустое состояние «Мастер ждёт вашего действия» для кампаний, где вступление уже есть.
- Оставить интерфейс минимальным: при создании кампании можно добавить необязательный выбор тона или места, но не строить полноценный редактор мира.
- Решить, обновлять ли резюме после вступления. Если вступление сохраняется как сообщение, оно попадёт в историю и в следующий prompt.

**Как проверить.**

- Создание кампании даёт одно сохранённое вступление.
- При ошибке модели вступление всё равно сохраняется шаблонным текстом.
- Повторное открытие кампании не создаёт второе вступление.
- Вступление видно в истории и участвует в следующем ходе.

**Чего не делать.**

- Не генерировать вступление только на клиенте: оно не попадёт в историю и не будет доступно модели.
- Не оставлять пустой чат при ошибке модели.
- Не обещать «полный мир»: вступление — это текст и несколько сохранённых полей, а не симуляция.

## Шаг 4. Обрабатывать исследование окружения на уровне намерения

**Зачем.** Сейчас «я осматриваюсь» — просто текст. Мастер может ответить атмосферно, но система не отличает осмотр от разговора, атаки или перехода. Из-за этого нет предсказуемой связи между действием, описанием и проверкой.

**Что сделать.**

- Ввести классификацию намерения: осмотр, поиск, слух, взаимодействие с предметом, переход, разговор, другое. Сначала можно сделать правило на ключевых словах и синонимах; затем — вызов модели с фиксированной схемой ответа.
- Хранить минимальное состояние сцены: место, описание, видимые объекты, выходы, NPC, время, уже найденные детали. Это может быть отдельная таблица или JSON у кампании.
- Включать сцену в prompt и требовать от мастера описывать только то, что уже установлено. Если данных нет, мастер должен сказать об этом и предложить уточнить действие, а не придумывать мир.
- Для осмотра предлагать проверку Восприятия или Расследования, но не позволять модели назначать DC и не выдумывать результат. Решение о проверке и броске остаётся за сервером.
- Разделять два слоя: нарративное описание (что видно) и механику (какая проверка нужна). Это разные части ответа, и их не стоит смешивать в один непрозрачный текст.
- Не утверждать, что мастер «видит» мир, которого нет в сохранённом контексте. Если сцена не задана, честный ответ — «опишите, где вы находитесь» или «давайте начнём со сцены».

**Как проверить.**

- Фразы «осматриваюсь», «оглядываюсь», «прислушиваюсь», «обыскиваю комнату» дают описание на основе сцены, а не отказ «этого нет в правилах».
- Если сцена пуста, ответ не выдумывает конкретные объекты, а просит уточнение.
- Если нужна проверка, сервер предлагает её или выполняет по правилам; модель не придумывает d20.
- Ответ остаётся по-русски и в заданном формате.

**Чего не делать.**

- Не добавлять жёсткий список точных фраз: пользователь формулирует свободно.
- Не позволять модели выдумывать результаты проверок.
- Не хранить сцену только в тексте последнего сообщения: она потеряется при длинной истории.

## Шаг 5. Ввести политику контента

**Зачем.** Сейчас в коде нет ни правил, ни модерации, ни возрастного порога. При этом игра может затрагивать мрачные темы, насилие и предрассудки вымышленных групп. Нужны явные границы, а не надежда на модель.

**Что сделать.**

- Записать политику в явном виде. Разрешать: уместную грубую лексику, мрачное вымышленное фэнтези, повествовательное насилие, предрассудки вымышленных групп как часть сюжета. Запрещать: сексуальное содержание с несовершеннолетними, груминг и эксплуатацию; реальную ненависть, травлю и призывы к насилию; практические инструкции по реальному вреду и незаконным действиям; доксинг и утечки личных данных.
- Добавить системные правила в prompt, но не полагаться только на них.
- Добавить слой модерации на входе и выходе: классификатор или набор проверок, который может отказать, переформулировать или предложить безопасную альтернативу.
- Предусмотреть безопасный fallback: понятный отказ без раскрытия внутренних инструкций и без повторения опасного содержания.
- Ввести возрастной порог или подтверждение возраста. Решить, где его хранить и как не собирать лишние персональные данные.
- Учесть ограничения провайдера: облачная модель может отказать сама, локальная может не отказать. Один и тот же prompt может вести себя по-разному.
- Покрыть политику тестами: разрешённые примеры проходят, запрещённые блокируются, ложные срабатывания проверяются отдельно.
- Провести ручную проверку на Ollama: локальная модель не является гарантированным фильтром.

**Как проверить.**

- Запрещённые категории не попадают в ответ даже при обходных формулировках.
- Разрешённые мрачные сцены не блокируются без необходимости.
- Отказ не раскрывает системную инструкцию и не повторяет запрещённый текст.
- При отказе пользователь понимает, что произошло и как продолжить безопасно.

**Чего не делать.**

- Не считать системный prompt достаточной защитой.
- Не обещать «полную безопасность»: модерация — это слой с ошибками и ложными срабатываниями.
- Не хранить в логах чувствительный текст без необходимости.
- Не путать вымышленное насилие с инструкциями по реальному вреду.

## Шаг 6. После каждого этапа: тесты и ручная оценка

**Порядок работы.**

1. Добавить backend-тесты через существующие fake-провайдеры: чат, embeddings, кубик.
2. Прогнать `uv run pytest -q` и `uv run ruff check app tests`.
3. Прогнать `npm run lint` и `npm run build`, если менялся frontend.
4. Вручную проверить сценарии на Ollama.
5. Записать результаты и сравнить с baseline.

**Фронтенд.** Менять только минимально необходимое: выбор тона или места при создании кампании, показ вступления, отображение предложенной проверки. Не перестраивать интерфейс ради самого интерфейса.

**Приоритет.** Сначала шаг 1 и шаг 2, затем вступление, затем исследование, затем политика контента. Это соответствует пользовательскому порядку: сначала инфраструктурная ясность, потом три содержательные задачи.

## Итог

Сейчас это работающий вертикальный срез: React рисует интерфейс, FastAPI управляет пользователями, персонажами, кампаниями, проверками и доступом к данным, PostgreSQL хранит историю и векторы правил, а LLM пишет текст. Сервер контролирует броски и поиск правил; модель не управляет механикой.

Главные ограничения честно видны в коде: кампания начинается без сцены, свободный текст не классифицируется как исследование, состояния мира нет, лист персонажа не попадает в prompt, политики контента и возрастного порога нет. Ближайший порядок работы — сделать локальный путь и политику провайдера однозначными, зафиксировать baseline, затем добавить вступление, обработку исследования и политику контента.

Бесплатность относится к runtime-сервисам приложения: PostgreSQL в Docker, локальная Ollama и открытые библиотеки. Подписка OpenCode Go за $10 — отдельная стоимость для coding-агента; её нельзя подключать к игровому backend.
